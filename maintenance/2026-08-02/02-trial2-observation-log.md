## 3. 監視の構成

### 3.1 計測経路の監視

**引継ぎ §4.3 は「フェーズ境界ごと」を定めるが、§4.1 の判定基準は 30 秒である。** 受け口が落ちてもフェーズ境界に着くまで検知できず、**1 回目の真因 D と同じ構造が残る。**

これを埋めるため、`session-state.json` を **60 秒ごとに読むだけの監視プロセス**を 1 本、リポジトリ外（スクラッチパッド）で走らせている。ユーザーの承認済み（間隔はユーザーの指定）。

| 制約 | 遵守 |
|---|---|
| 2 つ目の受け口を起動しない | ポートを開かない。読むだけである |
| `session-state.json` を書き換えない | 読み取り専用で開く |
| 生の OTel ペイロードをリポジトリ配下に書かない | ペイロードに触れない。`session-state.json` に PII は含まれない |
| 出力先 | スクラッチパッド（リポジトリ外）の JSONL |

**判定条件:**

| 条件 | 意味 |
|---|---|
| `MISSING` | ファイルが無い。受け口が起動していない |
| `SINK_STALE` | `sink_heartbeat_at` が 90 秒以上古い。受け口が落ちた（受け口の書込周期は 30 秒であり、90 秒は 3 回分の欠落） |
| `SINK_ALIVE_NO_EVENTS` | 受け口は生きているが `last_event_at` が null。送信側が無効 |
| `MULTI_SESSION` | `sessions_seen` が 2 以上。混線している |
| `OK` | 上記のいずれでもない |

### 3.2 報告の受け方

**ユーザーが本セッションを呼んだときにのみ観測する**（ユーザーの指定）。走行セッションからの報告はユーザーが中継する。

### 4-1. 引継ぎ §3 の確認は生成物の鮮度を保証しない

`diff -rq framework-src` は**原本しか見ない。** 走行が実際に読むのは `setup.js` の生成物である。**原本が一致していても生成物が古い版のままという状態が原理的に作れる。**

トライアル側は §2.3 のとおり全件一致であり、**走行への影響はない。**

**副作用が 1 つある。** 本セッションの文脈に注入される `CLAUDE.md` は古い方である。**規則解釈を答えるときは `framework-src/ja/` を引き、注入分を根拠に使わない。**

### 4-2. 検証項目 #18 / #19 は、このアプリでは規則の検証にならない

**走行前に記録する。走行後に書くと後知恵になる。**

`framework-src/ja/process-rules/review-standards.md` の Naming 節に次がある。

| 行 | 内容 |
|:-:|---|
| 89 | レイヤー別の命名表。**Use Case の例が `ConvertUnit`** |
| 82 | 単位の但し書き。**対象外の例が `Quantity { amount, unit }`** |

**トライアルは unit-converter-cli であり、規則の例示がこのアプリの正解そのものである。**

したがって architect が `ConvertUnit` と書き、`Quantity` を対象外と判定しても、**それは規則を読んだことの証明にしかならない。規則が未知のドメインで機能するかは判定できない。**

**通った場合は「例示の写経で説明がつく」と記録する。「規則が効いた」と書いてはならない。** 落ちた場合のみ強い情報を持つ（例示があってなお外した）。
