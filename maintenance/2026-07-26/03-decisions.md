## 議題1 — 規模とプロファイル

### 決定

> **規模は維持する。現行の体制で不備がある部分をメンテナンスする。**

| 項目 | 決定 |
|---|---:|
| エージェント数 | 21（維持） |
| フェーズ数 | 8（維持） |
| file_type 数 | 33（維持） |
| プロファイル分割 | 行わない |

### 却下した案

サブエージェント G が提案した縮小案（5 エージェント / 4 フェーズ / 6 file_type / 800 行）。

**G の論拠:** 現行版の失敗モードは「静かな不遵守」であり、規則が恒久的にコンテキストに収まる縮小版ではその失敗モード自体が存在しない。

**却下の根拠:** 規模そのものが設計意図であり、削減ではなく「現行規模のまま正しく動くようにする」ことを選択した。

### 却下に伴い引き受けた課題

削減で解けたはずのものを、別の手段で解く必要が生じた。

| 課題 | 維持した場合の解法 | 送り先 |
|---|---|:-:|
| コンテキスト予算 | 規則の分割ではなく**参照範囲の明示** | 2, 9 |
| 17 エージェントが起動されない | **明示的な名指し起動の保証** | 2 |
| 33 file_type の学習コスト | **Tier による段階的必須化**（削除しない） | 6 |
| 規模区分が Standard で頭打ち | **Large / Critical 区分の追加** | 6 |

## 議題2 — 実行モデル

### 決定

> **メインセッションが進行統括を演じる（案A改）。環境変数に依存しない。**

`orchestrator.md` は残し 22 体の名簿も維持するが、**起動されるのではなくメインセッションが冒頭で読んで演じる。**

| 主体 | 責務 | 記憶 |
|---|---|---|
| メインセッション | 進行統括（何をいつ動かすか）＋ユーザー窓口 | 全期間の会話を保持 |
| technical-authority（新設） | 技術裁定・整合保証・ゲート判定 | 成果物から再構築 |
| orchestrator（再定義） | プロジェクト管理・状態記録・対ユーザー報告 | ファイルから再構築 |

### 実測した現状

| 事実 | 実測値 |
|---|---|
| 実行不能な「起動・依頼」記述 | **25 箇所**（kotodama-kun へ 11、review-agent へ 3、orchestrator 内 4、その他 7） |
| `/full-auto-dev` が名指しするエージェント | **4 体のみ**（review-agent 5 回、risk-manager / security-reviewer / license-checker 各 1 回） |
| 名指しされないエージェント | **17 体** |

**最大の発見:** `/full-auto-dev` の各フェーズ記述は 4 体を除きエージェント名を含まない命令形である。つまり現状は「メインセッションが自分で全部やる」設計であり、**「orchestrator が全エージェントを統括する」という定義と、唯一の実行入口が別物になっていた。**

### 却下した案と根拠

| 案 | 却下理由 |
|---|---|
| B（ネスト全面有効化） | 実測で **depth 4 の連鎖が 4 本**、および `feedback-classifier ⇄ field-issue-analyst` の**上限なし循環**が存在する。かつ `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 未設定時に**無言で失敗**し、本レビュー最大の failure mode を再生産する |
| C（ハイブリッド） | 規則が 2 通りになり、どちらのモードで動作しているかをエージェントが判定できない |
| D（depth 2 のみ有効化） | 環境変数依存が残る。技術統括の新設により「統括者が独立主体でなければならない」という案 D の主な利点が消滅した |

### 採用の根拠

1. **同じ失敗モードを再生産しない。** 案 B は設定ファイル 1 つの欠落で無言に壊れる。案 A は起動が実行入口に露出し、失敗が可視化される
2. **現状のコマンドからの距離が近い。** 案 A は既存構造に名指しを足す延長。案 B は一度も動いたことのない実行経路を新設する
3. **移植性。** README が 7 プラットフォームの対応表を公開している以上、Claude Code 固有機能への依存を中核に置けない
4. **仕様変更耐性。** ネストの既定値は v2.1.217 で変更された実績がある

### 確定した設計要点

| # | 要点 |
|:-:|---|
| 1 | エージェントの起動はメインセッションの専権。定義から能動的な起動記述を全廃する |
| 2 | 「依頼する」→「完了報告に要請を含めて返す」に統一（25 箇所） |
| 3 | `feedback-classifier ⇄ field-issue-analyst` の循環は、メインセッションが回数を数えて打ち切るループに変わる |
| 4 | kotodama-kun はフェーズ末に 1 回起動し全 Out を一括チェック（11 回 → 最大 8 回） |
| 5 | 各定義に「読むべき規則の節」を明記する |

## 議題2b — 技術統括の新設

### 決定

> **`technical-authority` を新設する（案E-3）。** 裁定・整合保証に加え、品質ゲート判定とフェーズ遷移の技術面判定を orchestrator から移管する。

| 項目 | 決定 |
|---|---|
| 名称 | `technical-authority` |
| model | `opus` |
| エージェント数 | 21 → **22** |
| 技術裁定の記録先 | `tech-decision` を新設（`decision` は orchestrator 所有のまま） |
| `infra/` の owner | architect が `deployment-design`、implementer が `infra/` |
| orchestrator | プロジェクト管理と対ユーザー報告に専念 |

### 経緯

ユーザー提案「orchestrator はプロジェクト管理専門にして、ソフトウェア開発統括を設けるのは？」による。**個別に報告した 6 件以上の指摘が「技術統括の不在」という単一の原因に還元された。**

| 指摘 | 内容 |
|---|---|
| A5 | チェックリスト FAIL から重大度への写像が未定義 |
| A10 | design / implementation のルーティング判定基準がない |
| B5 | SCA/SAST クリアの判定主体が宙に浮いている |
| B7 | architect の Out が implementer の必要を満たすか誰も検査していない |
| A1 | ゲートが 3 回 FAIL した場合の打ち切り・waiver 判断者がいない |
| A6 | threat-model の生成をプロセスが指示していない |
| — | 性能・アクセシビリティ・可観測性の実装反映確認 |

### 責務境界

| エージェント | 立場 | やること |
|---|---|---|
| `architect` | **作る人** | design フェーズで Ch3-6・OpenAPI・可観測性設計を生成する |
| `review-agent` | **検査する人** | 規約（R1-R7）に照らして PASS/FAIL の指摘を出す |
| `technical-authority` | **決める人** | 技術判断を裁定し整合を保つ。FAIL の戻し先を決める |
| `orchestrator` | **回す人** | 状態記録・PM 情報の統合・対ユーザー報告 |

**review-agent との違いが最も重要。** review-agent は「R2.8 に違反している」と**指摘を出す**。technical-authority は「その指摘は設計起因だから design に戻す」「3 回目の FAIL なのでエスカレーションする」と**決める**。判定と決定の分離は R2.2 SRP と整合する。

### 記憶の問題の解決

議題 2 で「サブエージェントは記憶を持てない」を弱点として挙げたが、責務を分けると**記憶が要る統括と要らない統括**に分離できる。

| 統括 | 必要な情報 | 記憶 | 適所 |
|---|---|---|---|
| 進行統括 | 「3 日前にユーザーがこう言った」 | **要る** | メインセッション |
| プロジェクト管理 | WBS・コスト・リスク・状態 | 再構築可 | orchestrator |
| 技術統括 | 仕様・設計・コードの現物 | 再構築可。**新鮮な目で読むほうが良い** | technical-authority |

### 却下した案

| 案 | 却下理由 |
|---|---|
| E-1（裁定のみ、ゲート判定は orchestrator に残す） | orchestrator が PM 専門にならない。かつ**同一ゲートに 2 主体が関与**し、C3（SSOT 3 分裂）と同型の問題を新規に作る |
| E-2（成果物の所有も持たせる） | 「決める人」と「作る人」の混在で R2.2 SRP に抵触。裁定者が自ら作った成果物を裁定することになり独立性を失う。B2 の解決は architect + implementer への割当でも達成できる |

## 議題3 — ゲートの実効性

### 決定

> **機械検証は「検証器 1 本」に留める。** ゲート条件の妥当性判断は technical-authority（LLM）が担い、機械検証は「該当フェーズの合格レビューが実在するか」のみを検査する。

### 何を解決し、何を解決しないか

| 抜け道 | 塞がるか |
|---|:-:|
| technical-authority が review を作らずに「pass した」と報告する | **塞がる** |
| 規則がコンテキストから落ち、ゲートの存在ごと忘れる | **塞がる** |
| 前フェーズのゲートを飛ばして次フェーズの作業を始める | **塞がる** |
| review-agent が根拠の薄い `result = pass` を書く | 塞がらない（LLM 裁定に委ねる） |
| 指摘の重大度を軽く付けて High を回避する | 塞がらない（LLM 裁定に委ねる） |

G2（自己申告ゲート）に対しては二段で対処した。**(1) 採点者と被採点者の分離**（議題 2b）、**(2) 申告の実在性検査**（本議題）。内容の妥当性は LLM 判断であり、これは明示的に受容する。

### 検証器の設計原理

**宣言ではなく作業そのものを止める。** 「pass したと言ったか」ではなく「前フェーズのゲートを通らずに次フェーズのファイルを書こうとしたか」を見る。

| 書き込み先 | 必要なゲート |
|---|---|
| `docs/api/` `docs/observability/` `docs/security/` | G1 planning（R1） |
| `src/` `tests/` `infra/` | G2 design（R2/R4/R5） |
| `project-records/performance/` | G3 implementation（+ SCA/SAST） |
| `final-report.md` `docs/manual/` | G4 testing（R6） |

`project-management/` と `project-records/reviews/` は常に許可する（ゲート判定自体の書き込みを止めるとデッドロックするため）。

### 設計上の判断

| 論点 | 判断 | 理由 |
|---|---|---|
| フック不在時 | **LLM 裁定のみに縮退（安全側）** | 議題 2 で案 B を却下した理由は「無言で壊れる」こと。本検証器は**壊れず強制が効かなくなるだけ**で、故障の向きが逆 |
| ペイロード破損時 | fail open（通す） | 検証器のバグで全作業が止まる事態を避ける |
| 緊急脱出口 | `GR_SW_MAKER_SKIP_GATE_GUARD=1` | 誤検知でユーザーが完全に詰むことを防ぐ |
| ゲート条件の読み取り | **しない** | 妥当性判断は LLM の仕事。150 行に収まり、議題 6 の結論を待たずに実装できる |

### ゲート再試行と waiver（A1 の決着）

| FAIL 回数 | 対応 |
|---|---|
| 1-2 回目 | technical-authority が戻し先を決定し修正を要請 |
| 3 回目 | ユーザーへのエスカレーションを要請。waiver の要否を判断 |

waiver 成立の条件（すべて MUST）: ユーザー承認 / `tech-decision` に理由・影響・再評価時期を記録 / `final-report` の「既知の問題」への転記。

**`process-rules` §9.1 の「本ルールに例外はない」は、waiver を唯一の例外とする記述に改める。** 例外がないと書きながら実際には停止するしかない現状より、例外を明示して手続きを定めるほうが実効的である。

### `cannot-reproduce` と再現試行レポート（A4）

**決定:** `cannot-reproduce` を設ける。ただし「どう再現しようとしたか」「なぜ再現できなかったか」のレポートを必須とする。**目的は再オープン時の判断を可能にすること。**

これにより `cannot-reproduce` は行き止まりではなく**再開可能な中断**になる。

| # | レポート項目 | 再オープン判断への寄与 |
|:-:|---|---|
| 1 | 報告事象（現象・環境・操作・時刻） | 出発点の確定 |
| 2 | 試行記録（日時 / 環境 / 手順 / 結果 / 前回からの変更点） | 何を既に試したか |
| **3** | **変えた条件と変えなかった条件** | **未試行の軸が判明する** |
| 4 | 保全した証跡の所在 | 一次情報へ戻れる |
| 5 | 再現できない理由の考察 | 仮説の引き継ぎ |
| **6** | **再オープンのトリガー条件** | **判断基準を将来の読み手に引き渡す** |

**項目 3 と 6 がなければレポートは敗北記録に終わる。**

### defect-taxonomy の理論との関係

`defect-taxonomy-ja.md:70` は「再現できない SW の failure は、条件の特定が不十分なだけである」と断言する。**この理論記述は保持する。** ソフトウェアは決定的であり、理論として正しい。

衝突は理論と規範の混同から生じているため、適用範囲を限定する注記で解消する。

> 上記は failure の**性質**に関する理論的主張である。プロセス上は調査打ち切り基準を満たした場合に `cannot-reproduce` でクローズしてよい。これは「原因が存在しない」ことを意味せず、「**現時点の投入資源では未観測の状態変数を特定できなかった**」ことを記録するものである。

**むしろレポート要件（項目 3・5・6）は、この理論を実務手順に翻訳したものであり、理論と整合する。**

## 議題4 — 配布と二言語モデル

### 決定

> **原本を言語別ディレクトリ `framework-src/{lang}/` に再編する（案4-B）。**

```
framework-src/
  ja/  CLAUDE.md, user-order.md, agents/(22), commands/(5), process-rules/(11)
  en/  （同一構成）
```

### 根本原因

議題 4 配下の 10 件は、**1 つの設計判断から派生している。**

> 原本を `*-ja.md` / `*-en.md` というサフィックス付きで、**配布先と同じディレクトリに置く。**

### 構造的に解決するもの

**(a) リンクが原本ツリーと配布後ツリーの両方で正しくなる**

`framework-src/ja/process-rules/glossary.md` 内の `[不具合分類](defect-taxonomy.md)` は、原本ツリーでも配布後ツリーでも正しく解決する。**同一のリンク文字列が両方で機能する。** 現状は後者でしか解決せず、62 箇所の書き換えが必要だった。

**(b) `name` 衝突が構造的に不可能になる**

Claude Code が走査するのは `.claude/agents/`（およびネストした `.claude/` ディレクトリ）。`framework-src/ja/agents/` はパスに `.claude/` を含まないため走査対象外となる。

**(c) パリティ検査が単純になる**

```bash
diff <(cd framework-src/ja && find . -type f | sort) \
     <(cd framework-src/en && find . -type f | sort)
```

**(d) `.gitignore` から否定パターンが消える**

言語を追加するたびに `!*-xx.md` を足す必要がなくなる。

**(e) 翻訳の入出力が明確になる**

`framework-src/{src}/` → `framework-src/{target}/` の複製・翻訳。収集グロブを書く必要がない。

### 却下した案

| 案 | 却下理由 |
|---|---|
| 4-A（現行方式を個別修理） | **F7 だけで 62 箇所の個別修正**が必要。かつ「原本ツリーで正しくすると配布後ツリーで壊れる」トレードオフを生み、両立には配布時のリンク書き換えが要る |
| 4-C（サフィックス維持で原本を外へ） | P2 と F5 は解決するが F7 が残る |

### 対象外

| 対象 | 扱い | 理由 |
|---|---|---|
| `README.md` / `README-ja.md` | ルート据え置き | GitHub 表示に必要。かつ配布物ではない |
| `essays/*-{ja,en}.md` | サフィックス方式のまま | 配布物でなく読み物。パリティをベストエフォートに緩める対象 |

### リリース方針

> **ブランチ方式を採る。タグ運用は導入しない。**

| 項目 | 決定 |
|---|---|
| `create.js` の取得元 | `BRANCH = "main"` を維持（main = 安定版） |
| タグ / CHANGELOG | 導入しない |
| 今回の修正作業 | **作業ブランチで行い完了後に main へマージ** |

**根拠:** 著者は既に本フレームワークを使用している。main を壊すと自身の作業が止まるため、ブランチ規律が必要。一方、タグ運用のコストは現段階では利益を上回る。

## 議題5 — R7（純粋性）の矛盾解消と採否

### 決定

> **矛盾を解消した上で正式採用し、フレームワーク全体を R1-R7 に配線する。**

R7 は 9 項目 → **10 項目**（R7.10 を新設）。MUST 5 つは維持。

### 矛盾1 — R7.4 と R5.3 の衝突（A12）

**鍵は `spec-template:234` にあった。** R7.4 の意図は「結果がタイミング依存にならないか」と書かれている。つまり真の不変条件は**「処理の途中で外部状態が変化しても結果が変わらないこと」**であり、「全件をメモリに載せること」ではない。**文言が手段を規定してしまい、意図より狭くなっていた。**

**採用案:**

> 処理の途中で新たな外部読取を行わない。読取は処理開始前に完結させる。ストリーミング・ページネーション・早期終了により全件収集が不可能な場合は、**一貫性の単位（チャンク／スナップショット／トランザクション）を明示し、その単位内で収集→処理の順序を守る**

R5.3 との衝突が解消され、MUST の強度を保てる。「一貫性の単位を明示する」は成果物上で確認可能なので検証可能性も失われない。

### 矛盾2 — `throw` の扱い（A11）

厳密には二つの立場がある。

| 立場 | 主張 |
|---|---|
| (i) 純粋 | 同じ引数で常に同じ例外なら**参照透過は保たれる** |
| (ii) 非純粋 | 非局所脱出であり呼び出し側の推論を壊す |

現行 R7.2 は (ii) を採る。**これ自体は正当な立場**（`Either` を使う思想に連なる）。問題は (ii) を採りながら value object を純粋側と定めている点にある。

**採用案（例外規定 + 方向の提示）:**

> **例外の扱い:** ドメイン不変条件の違反を表す例外（値オブジェクトの検証等）は、同一引数で同一の例外を送出する限り functional core で許容する。I/O 失敗・システム起因の例外は imperative shell に限る。

加えて **R7.10（SHOULD・新設）**: functional core の失敗は可能なら戻り値型（Result / Either / Option）で表現する。言語が同等の機構を持たない場合はドメイン例外で代替してよい。

思想の方向を示しつつ、Java/C# での冗長さを強制しない。

### 矛盾3 — 直交性

`glossary-ja.md:88` は「レイヤー軸は純粋性軸と**直交する**」と明示的に主張しており、**この主張自体は妥当**である。しかし R7.2 の本文は「外側の層（imperative shell / **Adapter, Framework**）のみ」とレイヤー名を参照して両軸を結合している。

## 議題6 — 文書モデルの整合

### 版管理の一本化（C1 + C2）

**決定:** ファイル名は不変とし、版番号を Common Block に持たせる。`old/` へ退避するときのみファイル名に版を付ける。

```
docs/spec/my-app-spec.md              ← 参照はここに固定。document_version: 1.2
docs/spec/old/my-app-spec-v1.1.md     ← 退避時に版を付ける
```

**根拠:**

1. **議題 4 の決定と噛み合う。** ファイル名に版を持つ方式は版が上がるたびにリンクを壊す。仕様書は参照数が最多（implementer / test-engineer / technical-authority / review-agent の全員が In に持ち、traceability と handoff からも参照される）ため損害が最大

| `archived` | **書込み禁止（MUST NOT）。`old/` 配下の文書の状態** |

## 議題8 — 製品としての見せ方と計測

> **改訂（2026-07-31）— 本議題の「計測基盤の新設」は撤回する。**
>
> 本節は **「statusLine が唯一の計測手段である」という前提の上に設計されている。この前提が誤りであった。**
>
> | # | 誤り | 実測 |
> |:-:|---|---|
> | 1 | statusLine が計測器として使える | **デスクトップアプリでは発火しない。** 完全再起動後もプローブのログは 0 行 |
> | 2 | 他の公式手段は存在しない | **5 種類ある。** うち OpenTelemetry は同じ環境で動くことを実データで確認済み |
> | 3 | `context_used_pct` で引継ぎ閾値を判定できる | **OpenTelemetry に文脈の残量を表す指標はない。** 閾値は廃止し、圧縮の観測に置き換えた |
>
> **主経路を OpenTelemetry（`tools/otel-sink.mjs`）に置き換え、statusLine は CLI 限定の補助経路に降格した。** 根拠と実データは `maintenance/2026-07-31/03-measurement-path-poc.md`、規則への反映はプロセス規則 §3.2.7 / §4.0.3 にある。
>
> **副次効果の 3 件（A3 / B11 / A7）のうち A7（`context_used_pct >= 80` を再開の起動条件とする）も同時に撤回する。** A3 と B11 は経路が変わっただけで成立する。
>
> 以下は当時の記録として残す。

### 計測基盤の新設

ユーザー提案（フェーズごとのトークン提示 / コンテキスト 80% での引き継ぎ開始）は**両方とも実装可能**と判明した。

**設計: `statusLine` を計測器として使う。**

モデル自身はコンテキスト使用率を観測できないが、**statusLine スクリプトがファイルに書き、モデルがそのファイルを読めば**両目的が達成できる。statusLine は応答ごとに走るため、ファイルは最大 1 ターン分しか古くならない。

```
statusLine（各応答後）→ tools/session-meter.mjs
   → project-management/progress/session-state.json
      → メインセッションがフェーズ境界で読む
         ├─ cost と token を cost-log.json に追記
         └─ used_percentage >= 80 なら handoff を作成
```

### 採用しない方式

| 方式 | 却下理由 |
|---|---|
| サブエージェントの `<usage>` ブロック | **公式に文書化されていない実装詳細。** フィールド名・構造・入出力の別が未定義でバージョン間で壊れうる。かつメインセッション自身の消費が含まれない |
| セッション transcript（JSONL）の解析 | 公式に「エントリ形式は内部仕様でバージョン間で変わる」と明記 |
| `PreCompact` フック | トークン情報を受け取らず、compaction 決定**後**に発火する |

### 副次効果 — 実装不能判定の 3 件が覆った

| 指摘 | 旧判定 | 新判定 |
|---|---|---|
| A3 コスト予算 80% トリガー | 実装不能。閾値を目安に格下げ | **実装可能** |
| B11 `cost-log.json` に書き手がいない | owner 変更のみ | **実データが供給される** |
| A7 セッション再開の起動条件 | 未定義 | **`context_used_pct >= 80`** |

**A3 の指摘を訂正する。** 「エージェントは自分のトークン消費量を取得できない」はモデル直接では正しいが、statusLine 経由なら取得できる。閾値を格下げする必要はない。

なお A3 の他 2 件（30 分タイムアウト、defect 発見率の前日比）は依然実装不能であり、イベントベースへの置換という判断は変わらない。
