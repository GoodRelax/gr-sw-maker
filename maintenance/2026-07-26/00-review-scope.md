## 2. どんな観点でレビューしたか

7 領域を設定し、それぞれ独立したサブエージェントに担当させた。過去の Council Review（`council-review-2026-03-22-c.md` 等）が既に機械的整合性（見出し数・表行数・用語一致）を検証済みであったため、**同種の指摘を再報告しないことを全担当に指示**し、より深い層を狙った。

| 担当 | 観点 | 主対象 |
|:-:|---|---|
| A | プロセス設計の妥当性 | フェーズ定義、品質ゲート、状態遷移、条件付きプロセス、レビュー観点規約、不具合分類 |
| B | 文書体系と理論の整合 | 文書管理規則、仕様テンプレート、用語集、ANMS/ANGS エッセイ |
| C | マルチエージェント設計 | 21 体の定義、責務境界、ツール付与、引き継ぎ契約、モデル割当 |
| D | コードと配布 | 実行スクリプト、パッケージング、コマンド定義、秘匿情報 |
| E | 製品としての採用可能性 | README、CLAUDE テンプレート、移植ガイド、公開適性 |
| F | 二言語保守モデル | 42 ペアの構造一致、ドリフト率、保守コスト |
| G | 俯瞰評価 | 実行実績、競合ポジション、規模の妥当性 |

### 2.1 各観点で具体的に問うたこと

**A（プロセス設計）:** ゲートの exit criteria は LLM に実行可能か。ゲートが繰り返し失敗したときの loop-breaker はあるか。ロールバック・中断・再開・人間不在の状態は定義されているか。規則の量はコンテキスト予算に対して現実的か。

**B（文書体系）:** 33 の file_type それぞれに下流の消費者はいるか（write-only 文書の検出）。仕様変更が実装中に起きたとき版管理は破綻しないか。Form Block は機械パース可能か。理論（エッセイ）と実装（テンプレート）は一致しているか。

**C（エージェント設計）:** これらは LLM に対するプロンプトとして有効か。責務の重複・空白はないか。ツール付与は責務と一致しているか。引き継ぎの内容契約は定義されているか。21 体は 1 セッションで現実的に回るか。

**D（コードと配布）:** クロスプラットフォームで動くか。部分失敗・再実行時に何が起きるか。ユーザーの編集を破壊しないか。秘匿情報が配布物に混入していないか。この規模の Markdown 中心プロジェクトで実際に価値のある CI は何か。

**E（製品）:** README のクイックスタートを文字どおり実行すると成功するか。第三者が採用を判断する材料は揃っているか。公開すべきでない内部資料が混ざっていないか。

**F（二言語）:** 42 ペアは現時点でも一致しているか。直近のコミットは両言語に適用されているか。約 14,000 行 × 2 言語の手動同期は持続可能か。

**G（俯瞰）:** end-to-end で実行された証拠はあるか。LLM が 14,000 行の規則を守らない現実を前提に設計されているか。競合に対する差別化は防御可能か。8 フェーズ / 21 エージェント / 33 file_type は適正規模か。

## 3. 検証方法

| 方法 | 内容 |
|---|---|
| 静的解析 | 全文読解、grep による横断検索、行数・出現回数の実測 |
| 実地確認 | `setup.js` の挙動を scratchpad で再現、npm tarball の中身を `tar -tzf` で列挙、`git ls-files` / `git log --diff-filter` による追跡状態の確認 |
| 外部確認 | エンドポイントの疎通（curl）、GitHub リポジトリの実在確認、npm レジストリの照会 |
| 仕様照会 | Claude Code の公式ドキュメントを照会し、実装可能性を確認（結果は `ref-claude-code-constraints.md`） |

**推測と事実を区別する方針を採り、確認できなかった事項は §5 に明記した。**

## 4. レビュー中に訂正した自身の指摘

初期報告のうち 5 件は、実地確認により誤りまたは過大評価と判明した。**訂正内容も成果物に含める。**

| # | 初期報告 | 訂正後 |
|:-:|---|---|
| 1 | 同名エージェントが 3 件登録され 266KB を消費する | **1 件だけがロードされ、どれかは非決定的**（ファイルシステム読み取り順）。コンテキスト消費の記述は撤回 |
| 2 | 516KB がプロジェクト開始前にコンテキストを消費する | **過大評価。** サブエージェントは親の履歴を継承せず、`process-rules/` は Read して初めて載る。課題は「総量削減」ではなく「参照範囲の明示」 |
| 3 | R7.2 と R2.16 CA が重複し二重起票させる | **誤り。** 両者は直交する別観点。真の問題は R7.2 の本文がレイヤー名を参照して直交性を破っていること |
| 4 | `spec-template` の STFB 図が Ch1-4 なのに表が Ch1-6 で自己矛盾 | **言い過ぎ。** 図は剛柔グラデーション（Ch1-4）を示し、Ch5 は検証・Ch6 はメタでグラデーション外。読者に伝わりにくいが論理矛盾ではない |
| 5 | ANGS の `direction` 3 値は排他的でなく破綻している | **断定しすぎ。** 正しくは「`direction` が層番号から導出されるのか宣言されるのかが未記載」。導出なら破綻するが、宣言＋検証なら成立する |
| 6 | CLAUDE.md 末尾の MCBSMD はチャット規約でファイル生成と矛盾する | **誤り。** 見出しは「ドキュメントの基本形式」で最初から文書向け。真の問題は規約（囲め）と実践（囲んでいない）の乖離 |
| 7 | エージェントは自分のトークン消費量を取得できない | **モデル直接では正しいが、`statusLine` 経由なら取得できる。** コスト閾値は実装可能 |
| 8 | フレームワークは一度も実行された証拠がない | **誤り。** `gr-sw-maker-examples` が公開・実在し、かつ**著者は既に本フレームワークを使用している**。正しくは「本リポジトリに記録がなく README からもリンクされていない」 |

## 5. 未検証事項

本レビューで確認できなかった、または意図的に対象外とした事項を明記する。

| # | 事項 | 理由 |
|:-:|---|---|
| 1 | `/full-auto-dev` を end-to-end 実行した場合の挙動 | 実行にはトークン消費とユーザー承認が必要。**本レビューの指摘はすべて静的解析に基づく** |
| 2 | `gr-sw-maker-examples` の各プロジェクトの内部品質 | リポジトリの実在・公開状態・構成のみ確認。生成物の妥当性は未評価 |
| 3 | 他 AI プラットフォーム（Codex CLI / Gemini CLI 等）での移植可否 | 実機検証未実施。変換比率の算出はファイル数ベースの静的推定 |
| 4 | `essays/research/` の各調査レポートの事実正確性 | 競合フレームワークの現況は未検証。指摘は論理構造（循環定義）に対するもの |

| 7 | `Stop` フックの非ゼロ終了がセッションを実際に失敗させるか | 公式文書から確定できず。**採用した設計は `PreToolUse` のみに依存するため影響なし** |
