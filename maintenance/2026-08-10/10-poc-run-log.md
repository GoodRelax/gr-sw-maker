## D2 —— 開発方式が「利用者の選択」ではなく「エージェントの判定」になっている

**症状。** `1e` で technical-authority が開発方式を「簡易」と決め、そのまま `CLAUDE.md` へ記録して `1f`（免除）・`1g` へ進んだ。**利用者は方式を選ぶ機会を与えられていない**（`1h` で判定結果の確認は求められる。D2.2）。判定自体は妥当（単位換算 CLI で Critical 不成立）だが、**妥当な結論であることと、決めてよい主体であることは別である。**

**利用者の判断（2026-08-12）:** **開発方式は利用者が決める。** Claude Code は表 0 に照らした**判定結果と根拠を提案し、利用者の指示に従う。**

**本 PoC の「簡易」は、同日、利用者が事後に追認した。** 引継ぎ §2 が PoC の条件として簡易を挙げており、`1e` の判定内容そのものに異論は無い。**したがって以降の走行は利用者が決めた方式の上に乗っている。修正は PoC 後に行う**（走行中に作業表を変えると観測対象が別物になるため。これも利用者の判断である）。

### D2.1 これは走行の逸脱ではない

**規則どおりに走った結果である。** 利用者がどこに現れ、どこに現れないかを並べる。

| 出典 | 記述 | 利用者の登場 |
|---|---|---|
| プロセス規則 §3.1.1 | 「Phase 1 の `1e` で判定し、`CLAUDE.md`「開発方式」節に記録する（MUST）」 | **無し** |
| 作業表 `1e`（判定） | 依頼元 `main-agent` ／ 担当者 `technical-authority` ／ 返すもの「決めた方式と理由」 | **無し** |
| 作業表 `1h`（確認） | 依頼元 **main-agent** ／ 担当者 **利用者** ／ 返すもの **確認 / 差し戻し** | **有り。ただし `1e` `1f` `1g` の後** |
| `CLAUDE.md`「重要判断の基準」 | 「**予算やスケジュールに影響する判断**」は利用者に確認を求める | 有り |

**開発方式は 97 手順のうち何を実施し何を免除するかを決める単一のパラメータであり、コストと期間を最も強く左右する。**

### D2.2 芯は「判定」か「選択」かである

**当初この記録は「利用者の確認手順が無い」と書いたが、それは誤りであった。訂正する。** `1h` は作業表で 2 行あり、2 行目は **担当者 = 利用者・返すもの = 確認 / 差し戻し** である。**確認手順も差し戻し経路も定義されている。** 実走でも「承認して進むか」が利用者に問われた。

**残る欠陥は別の層にある。フレームワークは開発方式を「判定（derive）」としてモデル化しており、「選択（choose）」としてモデル化していない。**

- 表 0 は**基準表**であり、`1e` は**判定**手順である
- `1h` の確認は「**判定が正しく行われたか**」の確認であって、「方式を選ぶ」ではない
- 実走の報告文 §8 がそれを正直に述べた —— **「判断をお願いする点。ありません。Phase 1 の判定はすべて既定の基準に従って一意に決まっています」**

**この記述は判定モデルの下では正しい。** 基準に照らせば答えが一意に定まる以上、利用者に選ばせる余地は原理的に無い。**手抜きでも逸脱でもなく、モデルの帰結である。**

**利用者の裁定はこのモデル自体を変える。** 「根拠とともに提案し、利用者の指示に従う」は方式を**利用者が選ぶもの**に変え、表 0 を判定表から**提案の根拠**へ格下げする。

### D2.3 確認が守るべき分岐の下流にある

**`1h` は `1e` `1f` `1g` の後に走る。** その時点で `1f` は既に免除され、`1g` は方式を入力として条件付き 13 フラグを判定し終えている。**差し戻し経路はあるが、差し戻せば `1f` と `1g` をやり直すことになる。** 確認の位置が、それが守るべき分岐の下流にある。

**判定モデルのままなら順序はこれでよい** —— 一意に決まるものを確認するだけなら、いつ確認しても結果は同じだからである。**選択モデルへ移すなら順序が効いてくる。** 利用者が別の方式を選び得るなら、確認は分岐の前に無ければならない。

### D2.4 直す形と直す先

**フレームワークは既に「利用者が決める手順」の書き方を持っており、`1h` でそれを使っている。** 担当者 = **利用者**、依頼元 = **main-agent**、返すもの = 確認 / 差し戻し。`00-mode-matrix.md` の検査 15 が「`担当者` が `**利用者**` の行は `依頼元` が `**main-agent**` である」と定め、エージェントが利用者に直接話す経路を禁じている。**書き方を新たに考える必要は無い。`1e` に同じ形の行を足すだけである。**

**足す位置は `1f` より前である。** `1f` の免除・`1g` の判定・`1i` の pipeline-state・表 M の全分岐が `1e` の decision を入力にするためである。**`1h` の確認はそのまま残す** —— そこで確認されるのは Phase 1 全体の評価結果であって、方式単体ではない。

| 直す先 | 内容 |
|---|---|
| `00-mode-matrix.md` の `1e` 行（§4.2） | technical-authority を**提案**に限定し、**担当者 = 利用者の行を 1 本足して決定を移す**（`1h` と同じ形。返すもの = 選択 / 差し戻し）。**`split-work-table.mjs` で再生成する。生成物を手で直してはならない** |
| プロセス規則 §3.1.1 | 「`1e` で判定し記録する」を、**提案と選択の 2 段**に書き換える。表 0 の位置づけを判定表から**提案の根拠**へ改める |
| `CLAUDE.md`「重要判断の基準」 | 「開発方式の決定」を利用者確認の一覧に明記する。現状は「予算やスケジュールに影響する判断」に含意されるだけで、名指しされていない |
| `1h` の報告文 | **「判断をお願いする点」の扱いを見直す。** 選択モデルでは方式は「一意に決まる」ものではなくなるため、報告文が §8 に「ありません」と書けなくなる |

**本 PoC では未修正のまま進める。** 直せば走行中の作業表が変わり、観測が途中で別物になる。**修正は PoC 後、`08-poc-plan.md` の作業計画に段として足す。**

### D2.5 対照 —— 同じ `1e` で規則遵守は正しく働いた

**technical-authority は main-agent の誤った指示を拒んで是正を返した。** main-agent が `tech-decision` の書き先を `project-records/decisions/` と指定したのに対し、文書管理規則 §7 では `tech-decision` は `project-records/tech-decisions/`、`decisions/` は別 file_type（`decision`、owner: project-manager）の場所である。**黙って従わず申し送りを返し、実際にディレクトリは別々に存在した。**

**D2 はエージェントが規則を破った事例ではない。規則が求めていないことを、規則が求めていないという理由で行わなかった事例である。** 直すべきは規則の側である。
