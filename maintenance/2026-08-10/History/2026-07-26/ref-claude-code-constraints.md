# 参考 — Claude Code の実行モデル制約

**調査日:** 2026-07-26
**方法:** 公式ドキュメントの照会（2 回に分けて実施）
**位置づけ:** 決定ではなく**事実の記録**。複数の判断の根拠であり、実装中にも参照する。未確認事項は明示する。

---

## 1. サブエージェントのネスト

| 項目 | 事実 |
|---|---|
| 既定の挙動 | **サブエージェントはサブエージェントを起動できない。** Claude Code は全サブエージェントから Agent ツールを既定で取り上げる |
| 有効化方法 | 環境変数 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` を 2 以上に設定（`settings.json` の `env`） |
| `tools:` への記載 | ネストが有効な場合に**必要だが十分ではない**。`Agent`（旧称 `Task`）を列挙しても環境変数がなければ起動できない |
| 履歴 | v2.1.172 〜 v2.1.216 は既定で最大 5 層ネス可能だった。v2.1.217 で明示的な opt-in に変更 |

**未確認:** `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` の絶対上限は文書化されていない。

**判断への影響（議題 2）:** この方式は**採用しなかった**。実測で depth 4 の連鎖が 4 本、および `feedback-classifier ⇄ field-issue-analyst` の上限なし循環が存在するため、深さを上げるほど暴走が深くなる。かつ環境変数未設定時に無言で失敗する。

---

## 2. エージェントの同一性解決

| 項目 | 事実 |
|---|---|
| 識別子の由来 | **YAML frontmatter の `name:` フィールド。** 公式に「filename doesn't have to match」「Identity comes only from the `name` frontmatter field」と明記 |
| 同一ディレクトリ内で `name` が重複した場合 | **1 つだけがロードされる。** どれが選ばれるかは**ファイルシステムの読み取り順**に依存し、precedence は文書化されていない |
| ネストしたディレクトリ間の重複 | v2.1.178 以降、作業ディレクトリに最も近い定義が優先される |
| 検出手段 | v2.1.205 以降、`/doctor` が重複を報告する |

**判断への影響（議題 4）:** `porting-guide:52` の「ファイル名からエージェント名を導出する」は**事実誤認**であり、この誤情報の上に配布設計が乗っていた（P2b）。原本を `.claude/` の外（`framework-src/`）へ出すことで `name` 衝突が構造的に不可能になる。

---

## 3. サブエージェントの選択方法

| 項目 | 事実 |
|---|---|
| 既定 | メインセッションのモデルが `description` とユーザー要求の意味的一致で選ぶ |
| 明示指定 | プロンプト内で名指しできる（"Use the code-reviewer agent to..."） |
| @-mention | `@` でタイプアヘッド選択でき、そのタスクでの実行が保証される |
| 多数の類似 description | 公式は「明確で具体的な description を書け」と助言するのみ。**精度に関する保証も上限数の記載もない** |

**判断への影響（議題 2）:** 22 体の確実な起動を description の自動選択に委ねる根拠はない。**`/full-auto-dev` 内での明示的な名指しが唯一の保証手段**である。

---

## 4. スラッシュコマンドの命名

| 項目 | 事実 |
|---|---|
| コマンド名の由来 | **ファイル名（`.md` を除く）。** frontmatter ではない |
| `foo-ja.md` と `foo-en.md` の共存 | `/foo-ja` と `/foo-en` の 2 つの別コマンドになる。衝突しない |

**判断への影響:** コマンドには `name` 衝突の問題は存在しない。ただし D4 は有効 — `setup.js` 実行前は `/translate-framework` が存在せず `/translate-framework-en` しかないため、案内文が誤っている。

---

## 5. 実行の同期性と並列性

| 項目 | 事実 |
|---|---|
| 既定 | v2.1.198 以降、サブエージェントは**バックグラウンド実行が既定**で呼び出し元をブロックしない |
| 並列 | 複数のサブエージェントを同時に起動できる |
| 経過時間の観測 | **他エージェントの経過壁時計時間を観測する手段は文書化されていない。** `SubagentStart` / `SubagentStop` フックは存在するが経過時間メタデータは提供されない |

**判断への影響（A3）:** 「エージェントから 30 分以上応答がない」という監視トリガーは公式の手段では実装できない。イベントベースへの置換が必要。一方、**並列実行は可能**なので、メインセッション統括の下でも Agent Teams による並列実装は成立する（B15-b）。

## 6. コンテキストの継承

| サブエージェントが受け取るもの | 受け取らないもの |
|---|---|
| 自身の system prompt（= エージェント定義本文） | **親の会話履歴・ツール結果** |
| Agent ツールの起動プロンプト | 親の system prompt |
| プロジェクトの `CLAUDE.md` | プリロードされたスキル内容 |
| ツール定義 | — |

**判断への影響（議題 1 課題 B）:** レビュー初期報告の「516KB が実行時にコンテキストへ載る」「200k の過半をプロジェクト開始前に消費する」は**過大評価**である。

| 主体 | 自動的に載るもの | 概算 |
|---|---|---:|
| メインセッション | `CLAUDE.md` + 22 体の name/description + コマンド定義 | 約 20-30 KB |
| 各サブエージェント | 自身の定義（約 4KB）+ `CLAUDE.md`（16KB）+ 起動プロンプト | 約 20-25 KB |

`process-rules/` の 426KB は**自動ロードされない**。エージェントが Read して初めて載る。

したがって真の課題は「総量の削減」ではなく **「個々のエージェントが、自分の仕事に必要な規則の節をどう特定して読むか」** である。対処は各定義への「読むべき規則の節」の明記（Step 2-3 / 4-4）。

## 7. フック — 規則を「強制」する唯一の手段

| フック | 拒否できるか | 用途 |
|---|:-:|---|
| `PreToolUse` | **できる** | `permissionDecision: "deny"` を返すか、シェルフックが exit code 2 で終了するとツール実行をブロックする |
| `PostToolUse` | できない | `updatedToolOutput` で結果を差し替えられるがブロック不可 |
| `UserPromptSubmit` | できない | `additionalContext` を注入できるがブロック不可 |
| `Stop` | 部分的 | 非ゼロ終了で失敗を報告できるが、既に行われた作業は取り消せない |
| `PreCompact` | **できる**（exit 2） | ただし**トークン情報を受け取らず**、compaction 決定**後**に発火する |
| `SubagentStart` / `SubagentStop` | — | サブエージェントのライフサイクル前後で記録・検査ができる |

**フックは既定では助言的であり、`permissionDecision: "deny"` または exit code 2 を返して初めて強制力を持つ。**

**未確認:** `Stop` フックの非ゼロ終了がセッションを実際に「失敗」させるのか、単にログするだけなのかは文書から確定できなかった。**採用した設計は `PreToolUse` のみに依存するため影響しない。**

**判断への影響（議題 3）:** G2「ゲートは採点対象と同じ LLM による自己申告制」に対する解決手段が実在する。`gate-guard.mjs` を `PreToolUse` に接続し、前フェーズのゲートを通らずに次フェーズのファイルを書く操作を拒否する。

## 8. コンテキスト使用率とトークン会計

| 項目 | 事実 |
|---|---|
| モデル自身による観測 | **不可能。** メインセッション・サブエージェントとも、自身のコンテキスト使用率を会話中に観測する手段はない |
| `statusLine` | **stdin で `context_window` と `cost` を受け取る。文書化済み・v2.1.132 以降で安定** |
| `statusLine` の実行タイミング | セッション開始時、**各アシスタント応答後**、`/compact` 完了後、権限モード変更時 |
| サブエージェントの `<usage>` ブロック | **公式には文書化されていない実装詳細。** 「メタデータトレーラーが返る」とのみ記載。フィールド名・構造・入出力の別は未定義 |
| セッション transcript（JSONL）の解析 | **公式に非推奨。** 「エントリ形式は内部仕様でバージョン間で変わる」 |

**`statusLine` が受け取る JSON（抜粋）:**

```json
{
  "context_window": {
    "used_percentage": 42,
    "remaining_percentage": 58,
    "total_input_tokens": 84000,
    "total_output_tokens": 1200,
    "context_window_size": 200000
  },
  "cost": {
    "total_cost_usd": 0.12,
    "total_duration_ms": 180000
  },
  "exceeds_200k_tokens": false
}
```

**判断への影響（議題 8）:** モデルは自身のコンテキストを観測できないが、**statusLine スクリプトがファイルに書き、モデルがそのファイルを読めば**フェーズ別のコスト報告とコンテキスト 80% での引き継ぎが実装できる。statusLine は応答ごとに走るため、ファイルは最大 1 ターン分しか古くならない。

これにより A3（コスト閾値）/ B11（cost-log の書き手）/ A7（再開の起動条件）の 3 件が実装可能になった。

**サブエージェントの `<usage>` ブロックは使わない。** 未文書化でバージョン間で壊れうる上、メインセッション自身の消費が含まれない。`total_cost_usd` のフェーズ前後の差分を取るほうが堅牢かつ総額になる。
