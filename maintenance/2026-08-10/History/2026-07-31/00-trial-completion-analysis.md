## 3. 完走が証明したこと

### 3-1. 2026-07-26 レビューの中心的な問いに答えが出た

当時の最大の発見は「**22 体のうち 17 体が一度も名指し起動されない**」であった。本試行は 8 フェーズ中 6 フェーズを実行し（Phase 2 と 7 は条件付きプロセス無効によりスキップ）、**全ゲートを通過して納品まで到達した。**

**「このフレームワークで完走できるか」に、実測で肯定の答えが出た。** これは設計上の期待ではなく、成果物として残った事実である。

### 3-2. 復旧機構が実際に働いた

セッション上限に **3 回**到達し、**3 回とも `handoff` と `pipeline-state` から復帰した。** 成果物の破損は発生していない。

議題6 で `pipeline-state` を規模によらず必須（Tier = core）に変更した判断（A7）は、**「クラッシュ後の復元手段が構造的にゼロになる」という理由づけのとおりに機能した。** 免除していれば 3 回とも作業が失われていた。

### 3-3. 脅威モデリングが実務で有効だった事例が取れた

THR-01（Windows 標準の `system32\convert.exe` とのコマンド名衝突）は design フェーズで **Low として受容**した脅威である。それが **testing フェーズで予測どおりの形で顕在化**し、`deployment-design` 4.3 に用意してあった切り分け手順で解決した。

**受容した脅威を「起こらないもの」として扱わず対処手順を用意しておいたことが功を奏した。** 脅威モデリングの費用対効果を疑う根拠を、本試行は与えていない。

## 4. 完走が証明しなかったこと

**上記 3-4 を「前倒しの投資が回収された」と読むことはできない。** 比較対象が存在しないためである。

同じ CLI を軽い手順で作った場合に defect がいくつ出たかは、本試行のデータからは分からない。**「3,958 行の仕様が 0 defect を買った」も「3,958 行のうち大半は余剰だった」も、この 1 本の走行からは等しく支持されない。**

**単一の走行は反実仮想を与えない。** 費用対効果の判断には、軽い手順での対照走行が要る。**これは本試行の失敗ではなく、設計上できないことである。**

## 6. 新たに判明した欠陥

### FF-07（新規）: `pipeline-state` に終了状態が存在しない

**本分析で発見した。ふりかえりにも final-report にも記載がない。**

**証拠:**

```text
project-management/pipeline-state.md
  最終 change_log entry   2026-07-30T22:06:38Z
  step                    ready-for-gate-delivery-request
  phase_progress          6/7
  gate_result             pending          <-- PASS に更新されていない

project-records/tech-decisions/tech-decision-008-20260730-221144.md
  作成                    2026-07-30T22:11:44Z   <-- pipeline-state の 5 分後
  verdict                 PASS
```

**プロジェクトは完了したが、状態記録は「ゲート判定を要請できる状態」のまま止まっている。**

**根本原因は運用の抜けではなく値域の欠落である。** 文書管理規則 §9.1 の 15 フィールドを検査した結果:

| フィールド | 値域 | 完了を表せるか |
|---|---|:---:|
| `phase` | int **0-7** | 表せない（7 は operation フェーズであって「完了」ではない） |
| `step` | string（**値域の定義なし**） | 規定がなく、書き手ごとに任意 |
| `phase_progress` | string「完了/全体」 | 表せない |
| `gate_result` | enum `pending` / `pass` / `fail` | ゲート単位であってプロジェクト単位ではない |
| `blocked` / `needs_human` | boolean | 表せない |

**完了したプロジェクトを表現するフィールドが 1 つも存在しない。** そのため最終ゲートの PASS を書き戻す先がなく、**遷移先フェーズが存在しない（Phase 7 スキップ）ことで遷移の契機も発生しなかった。**

**実害:** いまこのプロジェクトのセッションを再開すると、`pipeline-state` を読んだエージェントは **GATE-DELIVERY が未判定であると解釈し、判定を再要請する。** §4.0 が定める再開手順が、完了済みプロジェクトに対して誤った再開を導く。

**同型の先例:** `tech-decision:verdict` に「非該当」がない（TD-003）、`final-report:total_cost_usd` に「計測不能」がない。**いずれも「値域が現実の状態を表現できない」という同じ型である。** 本件はその 3 例目にあたる。

### FF-06 の確定: 計測経路は全期間を通じて一度も動かなかった

`session-state.json` は **7 フェーズ + delivery を通じて一度も生成されなかった。** 結果:

| 品質目標 | 判定 |
|---|---|
| コスト予算アラート閾値 | **判定不能**（予算額が未定義、かつ消費が計測不能） |
| コンテキスト使用率の引継ぎ閾値 | **判定不能** |

`final-report:total_cost_usd` は必須の number 型だが、orchestrator は **値域外と承知のうえで `計測不能` と記録した。** `0` と書けば「コストが 0 であった」という誤った測定結果の主張になるためである。**推測を書かない規律が値域の欠落より優先された。判断としては正しい。**

**「トークン消費が大きい」というユーザーの実感は、最後まで数値で確認できなかった。**

### 非採用語の混入が 4 回、うち 1 回は自己矛盾

setup / planning / design / **delivery** の 4 フェーズで独立に発生した。**delivery では「非採用語を用いていない」という宣言そのものが該当語を含む**という構造に、pipeline-state / final-report / runbook / user-manual の**複数の書き手が独立に踏み込んだ。**

**最終的に仕様書全体では 0 件に解消している。** kotodama-kun は機能しているが、**同じ誤りが 4 回起きたことは、検出ではなく予防の側に穴があることを示す。**

### 伝聞の検証に非対称がある（retrospective-003 §4-2）

| 状況 | 検出できたか |
|---|---|
| 受け手が**成果物を改変する**行為を求められた 3 件 | **実害の前に検出**（一次資料に当たる動機が生じる） |
| 記録として受け渡された**伝聞由来の断定** 3 件 | **検出できず。** review-agent の再レビューまたは technical-authority のゲート判定という**事後の安全網でのみ**検出 |

**改変を伴わない受け渡しには検証の動機が生じない。** 「受け手が一次資料に当たる」という規律は、動機がある場面でしか働かない。
