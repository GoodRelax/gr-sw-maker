## 3. 施策 1 — 仕様書の質（量ではない）

**ユーザーの指摘により、方針を「量に歯止め」から「質の基準」に改める。**

### 3.1 判定基準

> **書くべきは、有能な後段エージェントが 2 人いたとき、**別々の答えに至りうる**ところだけである。**
>
> **同じ答えに至るなら、書かない。それは記述ではなく複製である。**

**「後のエージェントが分かることを書かない」を運用可能にした形である。** 「分かる／分からない」は主観だが、**「2 人が一致するか」は反例を 1 つ挙げれば決着する。**

### 3.2 書くべきもの — 後段が復元できない情報

| 種別 | 例（2 回目トライアルより） | なぜ復元できないか |
|---|---|---|
| **外から来た値** | 単位係数の一次定義（§3.4.5、70 行） | 外部の定義であり、導出できない |
| **他でもありえた判断と理由** | ADR 一覧（§3.6.2、97 行）、ADR-000 | コードは「何をしたか」を語るが「なぜ他を採らなかったか」を語らない |
| **却下した選択肢** | 増やさなかった 9 要素、§3.6.5 の「該当なし」11 件 | **最も失われやすい。** 記録がなければ次の担当が再検討する |
| **規則が決めていない箇所の決着** | FR-014 の丸めの同値ケース（ゼロから遠い側） | 規則に定めが無く、誰かが決めるしかない |
| **エージェント間の契約** | 公開面の宣言（§3.3.2） | 別のエージェントが実装する側と使う側を書くため、明示が要る |
| **ユーザーの回答** | インタビュー由来の要求、承認の事実 | 人間にしか出せない |

### 3.3 書くべきでないもの — 後段が復元できる情報

**以下は 2 回目の実物を判定した結果である。適用の可否は個別に判断する。**

| 対象 | 行数 | 復元できる根拠 | 判定 |
|---|---:|---|---|
| **Ch4 の Gherkin のうち、書式規則を機械適用すれば出るもの** | Ch4 836 行の一部 | §3.5.6 の出力書式規則と §3.4.4 の単位表から期待出力が計算できる | **要精査。** 規則が決めない場合だけ残す |
| **`3.4.1 クラス図`** | 93 | §3.2.2 責務表と §3.3.2 公開面表が同じ情報を持つ | **別記法の重複** |
| **`6.1 純粋性の分類`** | 52 | R7.6 が全関数に `@purity` タグを義務づけており、コードが持つ | **コードとの重複** |
| **`6.2` / `6.3` 設計原則の準拠確認** | 48 | review-agent が R1-R7 の Verdict を出す | **レビュー出力との重複** |

**注意:** 上表は「削れ」ではなく「**同じ情報が 2 箇所にある**」という指摘である。**どちらを正本にするかは別の判断であり、片方を消すときは参照の付け替えが要る**（文書管理規則 §6.1 の追随確認の対象）。

### 3.4 要求の層に削る力を置く

**2 回目の最大の発見:** `NFR-006`（109 単位対で文字列一致 100%）は `user-order.md` に無く、**Phase 1 のインタビューで生まれた。** それが厳密有理数を必要にし、2 コンポーネントを増やした。

仕様書 §2.3 の自己記録:

```text
全件がインタビューで合意された最小構成に対応する。
ラウンド 3 の Q11 でユーザーがインタビューを終了した時点で、
削減候補として挙げられた要求は 1 件も無い
```

**32 件すべて MUST、削減候補ゼロ。**

> **R2.18 は設計を最小構成と比較させる。要求を最小構成と比較させる機構が無い。**

**案:** インタビューの終了条件に「**削減候補の提示**」を加える。srs-writer が要求を確定する前に、「この要求を外すと何が起きるか」を各要求について 1 行で述べさせる。**外す判断はユーザーが行う。**

**これは質の施策であって量の施策ではない。** 要らない要求を落とせば、それを満たすための設計・テスト・レビューがまるごと消える。**乗数で効くのはここである。**

## 4. 施策 2 — レビューの再設計

**ユーザー指示:**

| # | 指示 |
|:-:|---|
| 1 | **design 完了前・実装開始前の 1 回**にする（抜け漏れ防止が目的） |
| 2 | **レビュワーが見るのは変化点だけ** |
| 3 | **レビュワーエージェントは起動を継続しておく** |

### 4.1 現状

design で**レビューが 3 回**回っている（`review-003` / `004` / `005`）。**1 回ごとに仕様書 2,908 行 + `review-standards.md` 511 行を読み直している。**

全走行では `review-001` 〜 `005` の 5 回。

### 4.2 3 の実現手段 — 継続起動は可能である

Claude Code のサブエージェントは通常 1 回ごとに新しい文脈で起動し、**そのたびに規約と仕様書を読み直す。**

**ただし継続する手段がある。** 一度起動したエージェントに追加の指示を送ると、**文脈を保ったまま続きを実行できる。** 2 回目以降は既読分がキャッシュに載っており、**読出（$0.50/M）で済み、書込（$10.00/M）が発生しない。**

**制約を 2 つ明記する。**

| 制約 | 内容 |
|---|---|
| **1 時間 TTL** | 間が空くとキャッシュが失効し、次のターンで全文が書き直される。**2026-07-31 の実測では 1 ターン $8.63、その 99.7% が `cache_creation`** |
| **文脈の単調増加** | 継続するほどレビュワーの文脈は伸びる。**読出は安いが 0 ではない**（$0.50/M） |

**したがって「継続起動」は無条件に安くはない。** 変化点レビューを短い間隔で連続して行う場合に効き、**フェーズをまたいで数時間空ける使い方では逆効果になりうる。仮説であり、施策 0 の計測で検証する。**

### 4.3 変化点レビューと追随確認の重複

**現状、同じことを 2 箇所でやっている。**

| 機構 | 契機 | 対象 |
|---|---|---|
| `C-3` 追随確認（文書管理規則 §6.1） | **生成時**（改訂した本人） | 図・ノート・影響を述べた行・ADR の Consequences・コード内の識別子 |
| review-agent | **事後** | 全文 |

**2 回目で `C-3` が実際に働いたことは確認済みである** — Ch3 の厳密有理数採用が Ch1.7 の L-7 の前提を壊したことを、レビュー前に自力で検出してユーザーに諮った。1 回目は同型の 7 件がすべて事後検出だった。

**したがって事後の全文再読は、生成時の追随確認と二重になっている。** 変化点に絞る根拠がここにある。

### 4.4 残る懸念

**変化点だけを見ると、変化していない箇所どうしの矛盾は見つからない。** 現状はそれを全文再読で拾っている。

**緩和案:** 1 回だけ残すレビュー（実装開始前）を**全文 1 回**とし、それ以外を変化点に絞る。**ユーザー指示の「design 完了前・実装開始前の 1 回」はこの位置にあたる。**

## 5. 施策 3 — エージェントが読む規約を絞る

**8,193 行が毎回の固定費である。** 上位 2 文書で 59.1%。

### 5.1 手段の比較

| 案 | 内容 | 長所 | 短所 |
|:-:|---|---|---|
| **A** | 大きい 2 文書を章単位のファイルに分割し、エージェント定義に「読む章」を書く | **確実。読む範囲が定義で固定される** | ファイル数が増える。`check-links` の参照更新が要る |
| **B** | **スキルに書く**（必要時に読み込まれる） | **段階的な開示ができる。** 本体を小さく保てる | **読み込みがモデルの判断に依存する。** 必要な条を読まない可能性がある |
| **C** | 現状維持 | 変更が要らない | 930 起動すべてに 8,193 行が乗る |

### 5.2 検討

**B（スキル）は魅力的だが、規約には向かない面がある。** スキルは「必要と判断したら読む」機構であり、**MUST の条文を読まなかった場合に違反が黙って通る。** 施策 0 の計測では違反は検出できない（コストしか見ない）。

**A は確実だが、分割の粒度を誤ると「必要な条が別ファイルにあって読まれない」という同じ失敗になる。**

**折衷案:** **MUST の条文と、判定に使う表は本体に残す。** 解説・背景・例示をスキルまたは別ファイルへ出す。**「なぜ」を分離する。**

**ただしこれは B-7（既定値と MUST に理由を併記する）と正面から衝突する。** B-7 は「理由が書かれていない規則が繰り返し読み替えを必要とした」ことを根拠に採用された。**理由を遠ざけると、その効果が失われうる。**

> **未解決。** 「理由は判断のときに要るが、毎回読む必要はない」が成り立つかは検証されていない。**施策 3 は施策 1・2 より後に置く。**

## 7. 施策 4 — 1 時間 TTL をプロセスに書く

**ユーザー判断: 採用。**

### 7.1 事実

キャッシュの TTL は 1 時間である。**失効後の最初のターンで、文脈がまるごと書き直される。**

```text
cache_creation  $10.00 / 100万トークン   （読出の 20 倍）
cache_read       $0.50 / 100万トークン

2026-07-31 の実測: 1 ターンで $8.63、その 99.7% が cache_creation
```

**避ける手段は無い。時間が経てば必ず失効する。** したがって規則は「失効させるな」ではなく、**「失効した後にどう振る舞うか」**を定めるものになる。

### 7.2 規則の案

> **1 時間以上中断するなら、中断する前に `session-handoff` を作る。再開時は、handoff が列挙した文書だけを読み直す。**
>
> **文脈が残っている前提で再開してはならない（MUST NOT）。** 残っていても、失効していれば読み直しと同じ費用がかかっている。

**既存の機構に載る。** 共通手順 `Fc` は現在こう定めている。

```text
Fc. session-state.json の compaction_count が前フェーズより増えていたら
    文脈の圧縮が起きている。session-handoff を作成して再開点を残す
```

**契機に「1 時間以上の中断」を加えるだけである。** 圧縮と中断はどちらも「文脈が当てにならなくなる」事象であり、同じ手当てでよい。

### 7.3 handoff に足すもの

**`session-handoff` に「再開時に読む文書の一覧」を必須にする。**

**これが本施策の中心である。** 一覧が無ければ、再開したエージェントは**安全側に倒して全部読む。** 一覧があれば、そこだけ読む。

| 現状 | 案 |
|---|---|
| handoff は「どこまで進んだか」を書く | **加えて「再開に要る文書」を列挙する** |
| 再開側は何を読むべきか判断する | **列挙されたものを読む。判断しない** |

**副次的な効果:** §4.2 で「継続起動が安いかは 1 時間 TTL 次第で未検証」と書いた。**本施策はその不確実性を回避する** — 継続起動が生きていれば安く済み、失効していれば handoff に従って必要分だけ読み直す。**どちらでも破綻しない。**

## 8. プロセスの 3 モード（**退役 — §9 が置き換えた**）

> **本節は §9「プロジェクト形式の定義」に置き換えられた。** 用語（モード → プロジェクト形式）・ラベル（精密 → 厳密）・選び方（1 問 → 2 問）・仕様形式との関係が §9 で改まっている。**記録として残すが、参照してはならない。**

**ユーザー指示による。モード 1 と 2 の骨格はユーザーが定め、モード 3 の設計と全体の整合は本ノートの提案である。**

### 8.1 モード 1（最軽量）— 実測値がある

**対照実験がそのまま実装である。**

| 項目 | 実測 |
|---|---|
| 与える文書 | **3 件のみ** — 要求（`user-order.md`）/ Spec 書式（`spec-template.md`）/ レビュー観点（`review-standards.md`） |
| 規約の量 | **745 行**（現行フル 8,193 行の **9.1%**） |
| コスト | **約 $8.30**（フル走行 $247.23 の **3.4%**） |
| 所要 | 約 26 分 |
| 成果物 | 仕様書 1,129 行 / コード 596 行（9 ファイル）/ テスト 129 件（**全通過を確認済み**）/ README |
| フェーズ・ゲート・PM 記録 | **無し** |

**起動プロンプト（実測されたものにユーザー指示を加えた形）:**

```text
user-order.md に記載のツールを作れ。その際、仕様書も書け。
仕様書は spec-template.md の形式で書け。
仕様やコードを書く時は review-standards.md に準拠しろ。
細かいところは全部任せた。

メインセッションの文脈が溢れないよう、適宜サブエージェントを使え。
質問や意見があれば述べよ。
```

**「細かいところは全部任せた」が実際に働いている。** 権限を渡しているため、逐一の確認が発生しない。**それでいて「質問や意見があれば述べよ」が、コマンド名の衝突・規約準拠によるファイル数増・温度の非対称という 3 件の意見と 4 件の質問を引き出した。**

**この 2 文は対にして使う。** 片方だけでは、任せきりで確認が無いか、確認が多すぎるかのどちらかになる。

### 8.2 モード 2（通常）— ユーザー指示

| 項目 | 内容 |
|---|---|
| 記録 | **プロセスの記録は取る**（decision / review / risk） |
| レビュー | **設計完了・実装開始前の 1 回。** 変化点を見る（§4） |
| ゲート | **実装開始前の 1 点**（レビューと同じ位置） |
| 人間の確認 | 起動時の質問 + **アーキテクチャの確認**（現行 `3a2` 相当）+ 完了報告 |
| 与える文書 | モード 1 の 3 件 + **使う記録の書式だけ** |

**「使う記録の書式だけ」が §5（規約の分割）に依存する。** 現行の `full-auto-dev-document-rules.md` は 1,941 行で 37 の file_type を定義しており、**3 種類しか使わないのに全部読むことになる。**

> **モード分割は規約の分割なしには成立しない。** §5 を先送りにすると、モード 2 の読む量がモード 3 とほぼ同じになる。

### 8.3 モード 3（精密）— 提案

**「通常をもっとやる」ではない。質的に違うものを 1 つ足す。**

> **モード 3 の定義: 作った本人がいなくなった後に、第三者が検証できること。**

モード 1 と 2 は「良いものを作る」ためにある。**モード 3 は「良いものだと後から示す」ためにある。** 費用が正当化されるのは、**実際に第三者が検証する場合だけ**である。

| 追加するもの | なぜモード 3 だけか |
|---|---|
| **トレーサビリティ**（要求 ID → 設計 ID → テスト ID） | 「その要求が満たされた証拠はどれか」を他人が辿れる。**2 回目トライアルは記録 0 件であった** |
| **独立した検証者**（作る者と検査する者の分離） | 自己検査は監査に耐えない |
| **ゲート判定の記録**（`tech-decision`） | 通した判断そのものを検証対象にする |
| **承認主体の記録**（`human:` / `process:` / エージェント名） | 人間が確認した箇所を機械的に判定できる |
| **機能安全分析**（HARA / FMEA / FTA） | 条件付き。**安全規格が要求する場合のみ** |
| 全観点レビューを複数点で | 変化点レビューだけでは、変化していない箇所どうしの矛盾が残る（§4.4） |

### 8.4 モードの選び方 — 規模ではなく性質で選ぶ

| モード | 選ぶ条件 |
|---|---|
| **最軽量** | 自分または少人数で使う。短命。**壊れても作り直せる** |
| **通常** | 他人が保守する。長く生きる。**壊れると誰かが困る** |
| **精密** | failure が人身・金銭・個人情報に直結する。または**認証・監査・規制の対象** |

**規模で選ばない理由は実測にある。** 2 回目は Micro と判定され、免除をフル適用してなお $247.23 を消費した。**免除マトリクス 13 行はすべて成果物であり、フェーズ数・エージェント起動数・共通手順の回数を 1 つも減らさない。** 規模区分はコストの支配項に触れていない。

**v3 の B-4 も同じ結論に達していた** — 「規模ではなく性質で条件づけるべき」。

### 8.5 未解決 — 規模区分との関係

**現行には規模区分が 5 段（Micro / Small / Standard / Large / Critical）ある。モードを足すと軸が 2 本になる。**

| 案 | 内容 | 論点 |
|:-:|---|---|
| **M-1** | **モードが規模区分を置き換える** | 軸が 1 本になる。**ただし `§3.1.1` と免除マトリクスの書き換えが要る**。`Critical` は既に「規模ではなく性質」と注記されており、性質軸への移行と整合する |
| **M-2** | 両方を残し、対応表を定める | 変更が小さい。**しかし 2 本の軸が矛盾したときの優先が要る** |
| **M-3** | モードを規模区分の上位に置き、モードごとに免除マトリクスを持つ | 表が 3 倍になる。**真因 B に逆行する** |

> **M-1 を推す。** 実測が「規模区分はコストの支配項に触れていない」ことを示しており、2 本目の軸として温存する根拠が無い。**ただしこれは規則の大きな書き換えであり、ユーザーの判断を要する。**

### 8.6 3 モードの比較

**現時点で実測があるのはモード 1 のみである。他は未測定である。**

| 次元 | 最軽量 | 通常 | 精密 |
|---|---|---|---|
| 規約の量 | **745 行（実測）** | 未定（§5 の分割に依存） | 8,193 行相当 |
| フェーズ | 無し | 設計 / 実装 / 検証 | 現行 7 フェーズ |
| ゲート | 無し | **1 点**（実装開始前） | 各区切り |

| 人間の確認 | 起動時 + 完了時 | + アーキテクチャ | + ゲートごと |

## 9. プロジェクト形式の定義（案）

**用語:** `プロジェクト形式`。値域は **`簡易` / `通常` / `厳密`**。

**`仕様形式`（ANMS / ANPS / ANGS）と対になる語である。** 用語集の「紛らわしい対の区別」に登録する。

### 9.0 どの形式でも変わらないもの

> **作るソフトの正しさは変わらない。** 同じ要求からは同じ動作のものを作る。
>
> **変わるのは、後から誰にどこまで説明できるかである。**

**どの形式でも必ず作るもの:**

| 成果物 | 理由 |
|---|---|
| 動作するコード | 目的である |
| **仕様書** | 何を作るかを決めずに作れない。**形式によって章構成は変わるが、省かない** |
| テストとその結果 | 動くことの根拠である |

**この節は梯子読みを防ぐために置く。** `厳密` は「より正確なソフト」を作る形式ではない。**より多くの説明材料を残す形式である。**

### 9.0.1 全形式に共通する 2 つの原則

**原則 1 — レビューは「変えるのが高いもの」に当てる。安いものは機械に任せる。**

| 対象 | 変えるコスト | 誰が見るか |
|---|---|---|
| 設計 | **高い。** 後段がすべてその上に積まれる | **人（別のエージェント）** |
| コード | 低い。書き直せる | **テストと lint（機械）** |

**根拠は実測にある。** 対照実験の最後の自己点検は **PASS 39 / NA 8 / FAIL 0** で、**何も見つけなかった。** 一方、同じ規約は**執筆中に**コードを変えている — R3.1（外部 I/O のエラー捕捉）に従って `bin/unicon.js` にパイプ切断の処理が入った。

> **規約は「執筆の指針」としては効き、「事後の点検」としては効かなかった。**

**原則 2 — サブエージェントは起動のたびに読み直す。往復の回数がそのまま費用になる。**

2 回目の走行では、**サブエージェントがコストの 72.4%**（$178.94 / 688 リクエスト）を占めた。**1 回の起動ごとに規約と文脈を読み込むためである。**

したがって、

- **1 回の起動で完結する仕事に使う。** 往復するなら継続する（§7 の handoff 規則が効く）
- **「一度読めば済むもの」を出す。** 繰り返し参照するものはメインが持つ
- **成果物を書き換えている最中に、それを読むエージェントを起動してはならない（MUST NOT）。** 2 回目の走行が自らの失敗（Phase 1 の torn state）から採用した運用である

**形式が定めるのは「役割を定義するか」であって「サブエージェントを使うか」ではない。**

| 形式 | 役割の定義 | サブエージェントの使用 |
|---|---|---|
| 簡易 | **定義しない** | **メインエージェントに一任。** 規模が大きければメインの判断で使う（並列実装を含む） |
| 通常・厳密 | **指定する**（プロマネ・レビュワー等） | 指定された役割に従う。**同じ役割を複数同時に走らせてよい**（並列実装・並列テスト） |

**簡易でサブエージェントを禁じてはならない。** 簡易は「役割分担の設計を持たない」形式であって、「小さいものしか作れない」形式ではない。**規模が大きければメインが自分で分担を決める。**

**原則 3 — 原則 1・2 で挙げた注意は、どの形式でもサブエージェントを使うときに等しく効く。**

### 9.1 選び方 — 2 問で決まる

```text
1. あなた以外の人が、このソフトを保守するか
   （半年後の自分も「他人」に含む）

2. 開発に関わっていない人が、後から成果物を検証するか
   （監査・認証・提出など）

   1 いいえ / 2 いいえ  ->  簡易
   1 はい  / 2 いいえ  ->  通常
   2 はい              ->  厳密
```

**どちらの問いも、要求を書き下す前に答えられる。** 作るものではなく、置かれた文脈に依存するためである。**判定は決定的であり、AI の裁量が入らない。**

### 9.2 簡易

**選ぶ条件:** 保守する他人がおらず、第三者の検証も無い。**作り直しがきく。**

| 項目 | 内容 |
|---|---|
| **成果物** | 仕様書 / コード / テストとその結果 / README |
| **判断の記録** | **仕様書の中の ADR に書く。** 別ファイルにしない |
| **プロセス文書** | **持たない。** フェーズもゲートも無い |
| **レビュー** | **無し。** 規約は**執筆の指針**として渡す。事後の点検は行わない |
| **設計原則の準拠確認** | **「該当なし」とその理由だけ書く。** 守った項目の羅列は書かない |
| **検査** | テストと lint（機械）+ **人間が成果物を見る** |
| **サブエージェント** | **役割を定義しない。メインエージェントに一任する。**<br/>規模が大きければメインの判断で使ってよい（並列実装を含む） |
| **人間の確認** | 起動時の質問と意見、完了報告 |
| **読む規約** | 要求 / 仕様書の書式 / レビュー観点 の 3 件のみ |
| **中断からの再開** | **`pipeline-state` を持たない。** 成果物そのものから判断する |

**再開点を失うことを受容する。** 選ぶ条件が「作り直しがきく」なので、**受容と条件が整合している。**

**実測（対照実験 `unit-converter`）:** 規約 745 行。成果物は仕様書 1,129 行 / コード 596 行（9 ファイル）/ テスト 129 件（全通過を確認済み）。

### 9.3 通常

**選ぶ条件:** **他人が保守する。** 半年後の自分を含む。第三者の検証は無い。

**簡易に加えるもの:**

| 追加 | 理由 |
|---|---|
| **`decision`（判断の記録）** | 保守する人は「なぜこうなっているか」を知る必要がある。**コードは何をしたかしか語らない** |
| **`review`（レビュー報告）** | 下記のレビューの結果を残す |
| **`risk`（リスク台帳）** | 引き継ぐ相手に、既知の危うさを渡す |
| **`pipeline-state`** | 中断から再開できるようにする |
| **`session-handoff`** | **1 時間以上中断するときに作る**（§7）。再開時に読む文書を列挙する |

| 項目 | 内容 |
|---|---|
| **プロセス** | 設計 / 実装 / 検証 の 3 区切り |
| **ゲート** | **実装開始前の 1 点のみ** |
| **レビュー** | **実装開始前に 1 回。書いた本人ではないエージェントが、変化点を見る** |
| **コードのレビュー** | **人は見ない。** テストと lint が受け持つ（原則 1） |
| **サブエージェント** | **役割を指定する。** 最小はレビュワー 1 体。<br/>**レビュワーは起動を継続し、変化点だけを渡す。**<br/>同じ役割を複数同時に走らせてよい（並列実装・並列テスト） |
| **人間の確認** | 起動時 + **アーキテクチャ** + 完了報告 |
| **読む規約** | 簡易の 3 件 + **使う file_type の書式だけ** |

**レビューを別のエージェントにするのが、通常の中核である。** 自己レビューは自分の前提を検査できない。**逆に言えば、通常で増える手数の大半はここに集中させる。**

### 9.4 厳密

**選ぶ条件:** **開発に関わっていない人が、後から成果物を検証する。** 監査・認証・提出など。

**通常に加えるもの:**

| 追加 | 理由 |
|---|---|
| **`traceability`（要求 ID → 設計 ID → テスト ID）** | 「その要求が満たされた証拠はどれか」を他人が辿れる |
| **`tech-decision`（ゲート判定の記録）** | 通した判断そのものを検証の対象にする |
| **承認主体の記録**（`human:` / `process:` / エージェント名） | **人間が確認した箇所を機械的に判定できる** |
| **`defect` / `change-request`** | 見つかった不具合と変更の経緯を残す |
| **作る者と検査する者の分離** | 自己検査は第三者の検証に耐えない |
| 機能安全分析（HARA / FMEA / FTA） | **条件付き。** 安全規格が要求する場合のみ |

| 項目 | 内容 |
|---|---|
| **プロセス** | 現行の 7 フェーズ |
| **ゲート** | 各区切り |
| **レビュー** | 複数点 + 全観点（R1-R7）。**コードも人が見る** |
| **サブエージェント** | **役割を指定する。** 作る者と検査する者の分離が定義であるため、現行の体制に準じる。<br/>同じ役割を複数同時に走らせてよい。<br/>**コストの支配項であることを承知のうえで選ぶ**（2 回目の実測で 72.4%） |
| **読む規約** | 全件 |

> **免責（定義に明記する）:** 本形式は**検証に必要な材料を揃える。** 適合や安全を**保証しない。** 安全規格・認証への適合判定は人間が行う。

**この一文を定義から外してはならない（MUST NOT）。** 外すと「厳密形式で作れば安全」と読まれる。**フレームワークは、検証していない能力を主張してはならない。**

### 9.5 一覧

### 9.6 仕様形式は別の軸である

**仕様形式（ANMS / ANPS / ANGS）をプロジェクト形式で決めてはならない（MUST NOT）。作るソフトの規模で決める。**

**軸が違う。**

| 軸 | 何で決まるか |
|---|---|
| **プロジェクト形式** | **誰が読むか**（保守する他人がいるか、第三者が検証するか） |
| **仕様形式** | **どれだけの分量になるか**（1 コンテキストに収まるか） |

**簡易でも規模が大きければ ANPS を採る。** 収まらない仕様書を 1 ファイルに押し込むことはできない。**逆に厳密でも小さければ ANMS で足りる。**

| 仕様形式 | 選ぶ基準 | 状態 |
|---|---|---|
| ANMS | 1 コンテキストウィンドウに収まる | 使用可 |
| ANPS | 収まらない | 使用可 |
| ANGS | 大規模 | **未対応のまま** |
| **StrictDoc** | **要求が増える / 改訂が続く**（§9.7） | 検討中。**プロジェクト形式とは独立に選べる** |

### 9.7 StrictDoc の検討

**判断は手元の `StrictDocStarter`（`samples/`）の実物を読んで行った。**

**形式の実体:**

```text
[REQUIREMENT]
UID: HELLO-002
TITLE: UTF-8 日本語対応
STATEMENT: >>>
表示メッセージは UTF-8 でエンコードされた日本語文字列を含むことができること。
<<<
RELATIONS:
- TYPE: Parent
  VALUE: HELLO-001
```

`UID` と `RELATIONS` が一級の要素であり、`[GRAMMAR] IMPORT_FROM_FILE:` でプロジェクト固有のフィールドを定義できる（自動車 SOVD のサンプルが実際にそうしている）。複数ファイルにまたがる関係を持てる。

**賛成する理由 — 2 回目が最も明確に失敗したのがトレーサビリティである。**

| 観測 | 値 |
|---|---|
| 2 回目の `project-records/traceability/` | **0 件** |
| 義務づけている場所 | `CLAUDE.md`「必須プロセス設定」 |

**規則で必須としていたのに 1 件も作られなかった。** 手で維持するトレーサビリティは、実際には維持されない。**StrictDoc はそこだけを機械化する。厳密形式が要求するものの中心と一致している。**

**公式ツール（上流で確認した）:**

| 種別 | 内容 |
|---|---|
| `strictdoc export` | **HTML / JSON / RST / ReqIF（双方向）/ Excel（双方向）/ SDoc / HTML2PDF（実験的）** |
| `strictdoc server` | Web UI。`TRACEABILITY_SCREEN` / `DEEP_TRACEABILITY_SCREEN` / `SEARCH` |
| **MCP サーバー** | **存在しない**（2026-08 時点） |
| CLI の検索・クエリ | **無い。** 検索は Web UI の実験的機能のみ |

**JSON 出力の追加は `0.0.53`（2024-04-01）。約 2 年前であり、現行の 0.27 系まで継続している。枯れた機能である。**

**JSON 出力が、書くコストと辿るコストを分ける:**

```text
書く    .sdoc     1 要求 7〜8 行（markdown の表 1 行より高い）
辿る    JSON      strictdoc export --formats json を 1 回
                  要求・UID・関係の木が 1 つの構造になる
```

**`.sdoc` を AI に直接読ませる必要はない。** 影響範囲を知りたいときは JSON を読む。**2,908 行の散文を読み直さなくてよい。**

**MCP サーバーが無いことは、この用途では障害にならない。** 欲しいのは「関係グラフを一度読む」ことであり、**常駐プロセスより、バッチで JSON を吐かせるほうが合っている。**

**懸念:**

| # | 内容 |
|:-:|---|
| 1 | **書くトークンは増える。** 1 要求あたり、markdown の表 1 行に対し `.sdoc` は 7〜8 行。**ただし辿るトークンは JSON 出力で下がる。** 粗い試算では、要求 32 件で追加 192 行に対し全文再読 1 回が 2,908 行であり、**関係を 7 回辿れば元が取れる。仮説である** |
| 2 | **外部依存が増える。** Python + StrictDoc。**`StrictDocStarter` が存在すること自体が、Windows での導入が単純でないことの証拠である**（proxy・winget・UAC・Mark-of-the-Web への対処が README に書かれている） |
| 3 | **器が変わる。** v3 で採用を決めた OKF（YAML frontmatter の Common Block）と `.sdoc` は別の容器である。**仕様書だけが別形式になり、他の file_type は markdown のまま残る** |
| 4 | **自前の検査ツールが届かない。** `check-links` / `check-tagnames` / `check-terms` は markdown を前提にしている。`.sdoc` は対象外になる（StrictDoc 自身の検査はある） |

**観察 — StrictDoc は ANGS の現実解かもしれない。**

ANGS は「GraphDB + Git、MD はビュー」と定義され、**研究段階として未対応**のまま置かれている。StrictDoc は GraphDB ではないが、**要求の関係グラフをテキストで持ち、ツールで検査する。** ANGS が狙っていたものに、実在する実装として最も近い。

**ANGS を未対応のまま残して StrictDoc を別の値として足すか、ANGS の実体を StrictDoc とするか。** 判断が要る。

**観察 2 — v3 が「過大」として却下した案が、外部から手に入る。**

v3 §4.3（真因 C: 改訂に突き合わせの義務がない）の対策案 **C-4** はこうだった。

```text
C-4  トレーサビリティを機械化する（参照グラフで影響先を算出）
     却下理由: ANGS 相当の基盤が要る。過大
```

**StrictDoc の JSON 出力は、その基盤を自前で作らずに得る手段である。**

2 回目で `C-3`（追随確認）が拾った L-7 の前提崩れは、**エージェントの注意深さによるものだった。** JSON があれば、影響範囲の算出が**判断ではなく計算**になる。

**推奨:**

> **仕様形式の値域に足し、簡易・通常・厳密のいずれでも選べるようにする。既定にはしない。**
>
> **選ぶ基準はプロジェクト形式ではない。要求の件数と、関係を辿る回数である。**
>
> - 要求が少なく、一度書いたら改訂が続かない → markdown
> - **要求が増える、または改訂が続く → `.sdoc`**
>
> **仕様形式（§9.6）と同じく、プロジェクト形式とは独立の軸である。**

**決める前に測りたいこと:**

| # | 内容 |
|:-:|---|
| 1 | **書くコストと辿るコストを分けて測る。** 同一内容を markdown と `.sdoc` で書いた分量（書く側）と、影響範囲の算出に要する読み込み量（辿る側）。**JSON 出力を前提にすると、2 つは別々に測らなければ意味がない** |
| 2 | **Common Block / OKF との併存の設計。** 仕様書だけ別容器で回るかどうか |
| 3 | **`StrictDocStarter` の検証済み版は `0.23.1`、上流の現行は 0.27 系。** 差分の確認が要る |
