## 2. §5 の結果

### 5.1 `.md` の記法 — 通るが、要求にはならない

**問い:** StrictDoc の Markdown 文書は通常の markdown からどれだけ離れているか。

**やり方:** `.sdoc` を書き、`strictdoc export --formats=markdown` に `.md` を出させ、それを入力に戻した。**正準の記法は StrictDoc 自身が教える。**

```
$ strictdoc export --formats=markdown --output-dir out src
$ cat out/markdown/01-req.md
# Probe Document

**UID**: DOC-PROBE \
**Version**: 1.0 \
**Date**: 2026-08-04

## Top level requirement

**UID**: REQ-001

**Statement**: The system shall do the thing.
```

| 分かったこと | 内容 |
|---|---|
| **普通の `.md` は無改造で通る** | H1 で始まってさえいれば構文解析される |
| **ただし要求は 1 件も生まれない** | `SECTION` と `TEXT` になるだけである |
| 要求になる条件 | `UID`（または `MID`）**と** `STATEMENT` の**両方**。片方だけなら `SECTION`（`reader.py:800-830` で確認） |
| 暗黙の `STATEMENT` | 見出し直下の地の文は `Statement` として扱われる（公式ガイドの最小例。実行で確認） |
| 文法宣言 | `**Grammar**: x.sgra` または `**Grammar**: x.gra.md` |

**移行コストの所在:** 「通るようにする」ではなく「**要求ノードにする**」ところに全部ある。既存 markdown を要求文書にするには、要求 1 件ごとに見出しへ切り出し、`**UID**:` と `**Statement**:` を書く。**これは書き換えであって設定ではない。**

> **公式ガイドの Markdown 節は実装より古い。** 「node type をどう支持するか」「文法とどう結びつけるか」を *open points* として挙げているが、0.27.1 では `**Type**: FINDING` も `**Grammar**:` も実際に動く。**公式文書だけを見て「まだ無い」と判断すると誤る。**

### 5.2 JSON の中身と大きさ — 復元できる。小さくはならない

**復元性:** 要求・UID・関係・カスタムフィールドはすべて JSON から取れる。**「辿るのは JSON」は成り立つ。**

**大きさ:** `samples/sovd-automotive-ja/`（13 文書・要求 122 件・カスタム文法・Mermaid・トレーサビリティ）で実測。

| 成果物 | ファイル | バイト | 文字 | 行 | トークン | `.sdoc` 比 |
|---|---:|---:|---:|---:|---:|---:|
| `.sdoc` ソース | 13 | 178,614 | 127,268 | 6,405 | **56,815** | 1.00 |
| `.sgra` 文法 | 1 | 2,530 | 2,530 | 127 | 781 | — |
| `.md` エクスポート | 13 | 196,326 | 144,980 | 6,480 | **62,042** | **1.09** |
| **JSON（`export` が出すそのまま）** | 1 | 576,432 | 576,432 | 8,811 | **158,667** | **2.79** |
| JSON（compact + 非 ASCII を素で） | 1 | 226,494 | 175,148 | 0 | 68,696 | 1.21 |

**JSON は元の `.sdoc` より小さくならない。丸ごと読むなら 2.79 倍である。** 原因はソースで確定した。

```python
# strictdoc/backend/json/json_generator.py:67
project_tree_json = json.dumps(project_tree_dict, indent=4)
```

`ensure_ascii` が既定の `True` なので**日本語が全て `\uXXXX` に展開**され、さらに 4 スペースで整形される。

> **`03-improvement-plan.md` §4.2 の「2,908 行の散文を読み直さなくてよい」は、JSON を丸ごと読む前提では成立しない。** 成立させるにはクエリで切り出す必要がある（→ 5.3）。

**Mermaid の寄与:** インライン Mermaid 14 ブロックは `.sdoc` 側 8,287 バイト、JSON 側は 9,242 バイト（JSON のエスケープ分だけ増える）。**JSON 全体 576,432 バイトの 1.6 % に過ぎない。**

> **§4.3 の「図を外に出せば要求グラフと JSON が軽くなる」は、実測では成り立たない。** 画像はもともと JSON に入らず、Mermaid は 1.5 % である。**図を外に出す理由は「人が読みやすいこと」に限られる。**

**`--included-documents`:** `DOCUMENT_FROM_FILE` で取り込んだ文書が**独立した文書としても重複**し、同じ UID が 2 か所に現れる（JSON 5,174 → 9,624 バイト）。**JSON を辿る目的では付けてはいけない。**

### 5.3 JSON のクエリー方法 — 7 種すべて書けた

**`StrictDocStarter/docs/03-sdoc-json-queries.md` に実出力つきで収めた。** 辿るコストの実測（対象は `sovd-automotive-ja`）:

| # | 取り出すもの | 出力トークン | `.sdoc` 全文 56,815 に対する比 | 標準機能で足りるか |
|:-:|---|---:|---:|---|
| 1 | 指定の章に属する要求の一覧 | 124 | 0.22 % | **足りる** |
| 2 | 指定 ID の要求の全フィールド | 186 | 0.33 % | **足りる** |
| 3 | 指定キーワードを含む要求 | 208 | 0.37 % | **足りる** |
| 4 | 上位要求（推移的に親を辿る） | 36 | 0.06 % | **足りる** |
| 5 | 下位要求（子を辿る） | 73 | 0.13 % | **足りる**（逆引きが要る） |
| 6 | 指摘箇所 | 24 | 0.04 % | **足りない。カスタム文法が要る** |
| 7 | 修正箇所 | 11 | 0.02 % | **足りない。カスタム文法が要る** |

**これが JSON の値打ちである。小ささではなく、答えだけを取り出せること。**

**Windows 固有の注意（実測）:** PowerShell は引用符の中の `"` を落とすため、`jq '...' file` の形は**そのままでは動かない**。`jq -f filter.jq file` なら PowerShell でも Git Bash でも同じに動く。`--arg` の併用も可。

```
PS> jq -r '[... select(._NODE_TYPE=="FINDING") ...]' index.json
jq: error: syntax error, unexpected ',' ...
    select(._NODE_TYPE==FINDING) | join(,)      <- " が消えている
```

### 5.4 フィールド設計

| 問い | 答え |
|---|---|
| 必須フィールド | **既定文法では REQUIREMENT の全フィールドが `REQUIRED: False`。** 公式の制約は「`STATEMENT` か `TITLE` のどちらかがあること」だけ |
| 足せるフィールド | **自由。** `.sgra` / `.gra.md` で `String` / `SingleChoice(...)` / `MultipleChoice(...)` / `Tag`。`- TAG: <名前>` で**新しいノード型**も作れる |
| **「指摘」を持てるか** | **標準には無い。カスタムノード型で持てる。** `[FINDING]` を定義し `ROLE: Reviews` で要求へ結んだ。JSON に出る |
| **「修正」を持てるか** | **標準には無い。カスタムフィールドで持てる。** `REVISION` を定義した。JSON に出る |
| **文書レベルのメタデータ** | **持てるが JSON に出ない。** ここが効く（下記） |

**文書メタデータの欠落 — 一次資料で確定。**

`DATE:` と `METADATA:` ブロックは `.sdoc` にも `.md` にも往復するが、**JSON にはまったく現れない。**

```python
# strictdoc/backend/json/json_generator.py:_write_document
# 書き出されるのは UID / VERSION / CLASSIFICATION / PREFIX / ROOT のみ。
# DATE と METADATA はこの関数に一切登場しない。
```

実測でも、`METADATA:` に `Author` / `Approver` / `Doc_Status` を置いた文書の JSON にそれらは 1 件も出なかった。

> **帰結: 機械で引きたい値は、文書メタデータではなくノードのフィールドに置く。**

### 5.5 タイトルと本文の使い分け

**公式の指針（`docs/strictdoc_01_user_guide.sdoc` を取得して原本で照合した。要約経由の文言は採っていない）:**

> "Every requirement should have its ``TITLE`` field specified."（1555 行目）
> "Every requirement shall have its ``STATEMENT`` field specified."（1583 行目）
> "…at least either the ``STATEMENT`` field or the ``TITLE`` field must be present."（1061 行目）

| 問い | 答え |
|---|---|
| **`TITLE` の文字数制限** | **強制されていない。推奨値も公式に無い。** ソース全体の長さ検査は `len(title) == 0`（空タイトル拒否、Web UI のフォーム）のみ |
| 長い `TITLE` を書くと | **HTML の目次にそのまま全文が出る。省略されない**（252 文字のタイトルで確認） |
| Markdown 形式では | **`TITLE` が見出しそのものになる** |

### 5.6 `.md` へのエクスポート — ある

**`strictdoc export --formats=` の選択肢は 11 種（`--formats=BOGUS` に対するエラーメッセージで確定）。**

```
choose from 'html', 'html2pdf', 'markdown', 'rst', 'json', 'excel',
'reqif-sdoc', 'reqifz-sdoc', 'sdoc', 'doxygen', 'spdx'
```

**`markdown` は 0.23.1 の選択肢にも同じく並んでおり、両版で実際に出力される。** 引継書 §5.6 が「未確認」としていた点は解決した。

**「`.sdoc` で書き、必要なときだけ `.md` に出す」は成り立つ。ただし往復は無損失ではない。**

| 往復で起きること | 内容 |
|---|---|
| 増える | `OPTIONS: MARKUP: Markdown` と `METADATA:` ブロック |
| 変わる | `>>> <<<` の複数行が 1 行に畳まれる。File 関係の `VALUE:` が `PATH:` になる |
| 失われる | **値そのものは失われない** |

**そしてカスタム文法では、出した `.md` を StrictDoc 自身が読み戻せないことがある。**

```
$ strictdoc export --formats=json rt
error: could not parse file: ...\01.md
Semantic error: Wrong field order for requirement: [UID, TITLE, SEVERITY, RESOLUTION, STATEMENT].
Hint: Problematic field: STATUS. Compare with the document grammar: [...]
```

Markdown reader が復元する順序が固定されているためで、文法をこの順に宣言していないと落ちる。

```
MID → UID → LEVEL → STATUS → TAGS（既知のメタ）→ TITLE（見出し）
  → カスタムの単一行フィールド → STATEMENT → 残りの複数行フィールド
```

**`samples/sdoc-patterns/` はこの順序で文法を宣言してあり、markdown 出力が構造無損失で読み戻せることを確認済みである。**

### 5.7 書くコストと辿るコスト

**書くコスト（同一内容を 2 通りで書いた比較）:** `.sdoc` 56,815 トークン に対し `.md` 62,042 トークン。**Markdown のほうが 9 % 多い。**

> 比較対象は `export --formats=markdown` が同じソースから機械的に生成した `.md` である。**人が書けばもっと短くなりうるが、それは別の変数が混ざる。同一内容であることを保証できるのはこの経路だけである。**

**辿るコスト:** 5.3 の表のとおり。クエリ 1 本の出力は `.sdoc` 全文の **0.02〜0.37 %**。

### 5.8 図の置き場

| 問い | 答え |
|---|---|
| `RELATIONS: TYPE: File` で図を結べるか | **結べる。** 任意のファイル（`.mmd` など）を指せる |
| 何が要るか | `strictdoc_config.py` に **`REQUIREMENT_TO_SOURCE_TRACEABILITY` と `include_source_paths` の両方** |
| **無いとどうなるか** | **エラーも警告も出さずにリンクが張られない。** JSON には関係が残るので、気づかない |
| 何が生成されるか | `_source_files/<path>.html`（**ファイルのソーステキストのページ**。図の描画ではない）と、要求からそこへのリンク |
| インライン vs 外出しの JSON 差 | **1.5 %。判断材料として意味を持たない**（→ 5.2） |

### 5.9 `0.23.1` → `0.27.1` の差分

**同梱サンプルは両版で動く。** `sovd-automotive-ja` の JSON は**バイト一致**、HTML も 54 ページで一致。`hello-strictdoc` も動く。

| 項目 | 0.23.1 | 0.27.1 |
|---|---|---|
| サブコマンド | `about export import manage new server version launcher` | **`import` が消え `convert` / `format` が増えた** |
| `project_features` | `RAPIDOC` **あり** | **削除** |
| **`MATHJAX` / `MERMAID`** | **明示指定が必要** | **既定で有効。列挙すると DEPRECATION 警告** |

## 3. gr-sw-maker 固有の論点

### 論点 1 — OKF / Common Block との併存

**`2026-07-31/01-trial-report_v3.md` §3.2 が採用を決めた OKF（YAML frontmatter）15 フィールド相当を `.sdoc` に持たせられるか。**

| 置き場 | 可否 | 根拠 |
|---|---|---|
| **ノードのフィールド** | **持てる。JSON からも引ける** | カスタム文法は自由。実測で確認 |
| **文書レベル（`METADATA:`）** | **持てるが JSON から引けない** | `json_generator.py` が書き出さない（5.4） |

**Common Block は文書レベルのメタデータである。** したがって素直に写すと**機械で引けなくなる**。取りうる形は 3 つ。

| 案 | 内容 | 代償 |
|---|---|---|
| A | Common Block を**文書先頭の 1 ノード**として置く（`[TEXT]` ではなくカスタムノード型） | `check-*` の frontmatter 前提が全て崩れる |
| B | **仕様書は Common Block を持たない `file_type` とする** | 例外が 1 つ増える。管理対象の一貫性が落ちる |
| C | Common Block は `.md` の frontmatter のまま残し、**要求本体だけを `.sdoc` にする** | 1 つの仕様が 2 ファイルに割れる |

> **どれも小さくない。** 「StrictDoc を採る」判断は、実質「Common Block の扱いを設計し直す」判断である。**この点は `03-improvement-plan.md` §4 が見積もっていない。**

### 論点 2 — 自前の検査ツールが届かない範囲

`tools/check-links.mjs` / `check-tagnames.mjs` / `check-terms.mjs` は markdown 前提であり、`.sdoc` は対象外になる。

| 検査 | StrictDoc で代替できるか |
|---|---|
| **リンク切れ（`check-links`、118 リンク + 269 節参照）** | **一部できる。** UID の参照先が存在しなければ StrictDoc がパース時に落ちる。**ただし節参照・相対パスは対象外** |
| **タグ名（`check-tagnames`）** | **できる。** `SingleChoice(...)` / `MultipleChoice(...)` が値域を強制する。**自前の検査より強い**（書けない時点で落ちる） |
| **用語（`check-terms`、非採用語の検査）** | **できない。** StrictDoc に本文の語彙検査は無い |
| `check-parity` / `check-roster` / `check-setup` | **対象外。** 仕様書ではなくフレームワーク自身の検査である |

> **`check-terms` を `.sdoc` に届かせる手段は自作しかない。** ただし `.sdoc` は行指向のテキストなので、既存の実装を拡張子で分岐させる程度で済む見込みがある。**未検証である。**

### 論点 3 — ライセンス

| リポジトリ | ライセンス |
|---|---|
| `StrictDocStarter` | **Apache-2.0** |
| `gr-sw-maker` | **MIT** |

**同一著作者だが、取り込み方の判断は要る。** Apache-2.0 は MIT に無い条項（特許許諾・NOTICE・改変告知）を持つため、**複製して取り込むなら帰属表示が要る。参照にとどめるなら不要。**

**判断は `license-checker` エージェントの責務である。** 本書は事実の提示にとどめる。

> **なお、今回の成果物は「`.sdoc` の書き方」と「jq の書き方」であって、gr-sw-maker が**コードとして**取り込む対象ではない。** 参照（リンク）で足りる可能性が高い。

### 論点 4 — 仕様形式の値域への追加

`ANMS` / `ANPS` / `ANGS` に対する StrictDoc の位置づけ。

**`ANGS` は「GraphDB + Git」と定義され未対応のままである。** StrictDoc は GraphDB ではない。

| 案 | 評価 |
|---|---|

| **別の値として足す** | **こちらが素直。** 「関係を機械で辿れる形式」という新しい軸が 1 本増える |

> **ただし `03-improvement-plan.md` §3.5 は「仕様形式は分量と、関係を辿る回数で決まる」としている。** StrictDoc を足すなら、**その選定基準に「関係を辿る回数」の閾値を数値で書く必要がある。** 現状その数値は無い。

## 5. 推奨 — 条件つきで採る。ただし今ではない

**決めるのはユーザーである。以下は根拠つきの推奨である。**

### 5.1 採る理由は 1 つに絞られた

**トレーサビリティの機械化である。** 2 回目トライアルの `project-records/traceability/` は **0 件**で、`CLAUDE.md` が必須と定めていたにもかかわらず作られなかった。**StrictDoc は、この基盤を自前で作らずに与える。**

**そして実測がそれを支持する。** 上位要求・下位要求・指摘・修正のどれも、**`.sdoc` 全文の 0.02〜0.37 % の出力で答えが出る。** 手で維持する必要が消える。

### 5.2 しかし当初の想定のうち 2 つは実測で否定された

| 当初の想定（`03-improvement-plan.md` §4） | 実測 |
|---|---|
| 「JSON なら 2,908 行の散文を読み直さなくてよい」 | **JSON を丸ごと読むなら 2.79 倍になる。** 成立するのはクエリで切り出す場合だけ |
| 「図を外に出せば要求グラフと JSON が軽くなる」（§4.3） | **Mermaid は JSON の 1.6 %。** 外に出す理由は人の可読性だけ |

**どちらも「採るべきでない」を意味しない。** 意味するのは、**採るなら「JSON をクエリする手順」を必ず伴わせること**である。JSON を丸ごと読ませる運用にすると、**現状より悪くなる。**

### 5.3 見積もられていないコストが 1 つある

**Common Block との併存**（論点 1）である。`03-improvement-plan.md` §4 はこれを扱っていない。**3 案のいずれも小さくなく、どれを採るかで `document-rules` の分割（段階 4）に影響する。**

### 5.4 推奨する順序

| # | 内容 | 理由 |
|:-:|---|---|
| 1 | **段階 1〜4 を先に進める。StrictDoc は着手しない** | §4.4 が「段階 1〜4 を妨げない」と書いたとおり。**逆も真で、段階 4（`document-rules` の file_type 分割）の結果が論点 1 の判断材料になる** |
| 2 | **段階 4 の設計時に、論点 1 の 3 案を明示的に検討する** | Common Block の置き場は file_type 分割と同じ問題を扱っている。**別々に決めると矛盾する** |
| 3 | **採ると決めたら、まず 1 つの仕様書で試す** | 2,908 行を一度に移さない。`samples/sdoc-patterns/` が型を示している |
| 4 | **仕様形式の値域には「別の値として足す」** | `ANGS` の定義を書き換えるより副作用が小さい（論点 4） |
| 5 | **取り込みは参照で行う** | 成果物は文書であってコードではない。Apache-2.0 の複製に伴う義務を負う必要がない（論点 3。**最終判断は `license-checker`**） |

### 5.5 採らない場合に失うもの

**公平を期して書く。** 採らなければ、**トレーサビリティは引き続き手で維持されることになり、2 回目の実績はそれが 0 件になることを示している。** `03-improvement-plan.md` の段階 1〜6 には、この点を解決する項目が無い。

> **「採らない」を選ぶなら、トレーサビリティを義務から外すか、別の機械化手段を立てるかのどちらかが要る。** 現状の「規則で必須とするが機械が支えない」形を続ける選択肢は、実測により否定されている。
