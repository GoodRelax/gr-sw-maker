# gr-sw-maker 改良計画

**目的:** ざっくりした要求からヒアリングを行い、仕様書付きの高品質なソフトを作る。**その品質を落とさずに費用を下げる。**

**位置づけ:** `01-trial2-summary.md`（2 回目トライアルの総括）と `02-token-reduction-plan.md`（検討の記録）を受けた**実施計画**である。検討の経緯・却下した案・訂正の記録は `02` にあり、本書はそこから実施事項だけを取り出す。

**前提となる実測:**

| 事実 | 値 |
|---|---|
| 2 回目（フル）のコスト | **$247.23**。GATE-DESIGN 通過後に終了し、**コードは 0 行** |
| 対照実験（規約 2 件 + 起動プロンプトのみ） | **約 $8.30 / 26 分。** 動作するツール・テスト 129 件全通過・仕様書 1,129 行 |
| コストの所在 | **design が 78.5%。サブエージェントが 72.4%** |
| モデル | **原因ではない。** 対照実験は `Opus 100%` |

## 1. 何を作るか

**プロジェクト形式を 3 つ用意し、規模区分（Micro / Small / Standard / Large / Critical）を置き換える。**

| 形式 | 選ぶ条件 | 作る量 |
|---|---|---|
| **簡易** | 保守する他人がおらず、第三者の検証も無い | **ほぼゼロ。現行ファイルのまま成立する** |
| **通常** | **他人が保守する**（半年後の自分を含む） | **本体。規約の分割が前提** |
| **厳密** | **開発に関わっていない人が検証する**（監査・認証・提出） | **現行 + 横断の変更のみ** |

**定義の全文は `02-token-reduction-plan.md` §9 にある。本書は重複させない。**

**選び方は 2 問で決まる。**

```text
1. あなた以外の人が、このソフトを保守するか（半年後の自分を含む）
2. 開発に関わっていない人が、後から成果物を検証するか

   1 いいえ / 2 いいえ  ->  簡易
   1 はい  / 2 いいえ  ->  通常
   2 はい              ->  厳密
```

## 2. 段階

**段階 1 から順に進める。各段階は独立に価値を持ち、途中で止めても損をしない。**

### 段階 1 — 簡易を単独で出す（規約の分割は不要）

**いま出せる。** 必要なのは現行のままの 2 ファイルと起動プロンプトだけである。

| 要るもの | 状態 |
|---|---|
| `spec-template.md`（297 行） | **現行のまま** |
| `review-standards.md`（511 行） | **現行のまま** |
| 起動プロンプト | **新規。数行** |

**起動プロンプト（対照実験で実測されたものに、サブエージェントの扱いを足した形）:**

```text
user-order.md に記載のツールを作れ。その際、仕様書も書け。
仕様書は spec-template.md の形式で書け。
仕様やコードを書く時は review-standards.md に準拠しろ。
細かいところは全部任せた。

メインセッションの文脈が溢れないよう、適宜サブエージェントを使え。
質問や意見があれば述べよ。
```

**「細かいところは全部任せた」と「質問や意見があれば述べよ」は対で使う。** 前者が逐一の確認を止め、後者が意見と質問を引き出す。**片方だけでは、任せきりになるか確認過多になる。**

**簡易が持たないもの:** プロセス文書・ゲート・役割の定義・事後のレビュー・`pipeline-state`。

**中断からの再開点を失うことを受容する。** 選ぶ条件が「作り直しがきく」なので、受容と条件が整合している。

> **この段階の成果は、次の対照走行の基準線になる。** 以後の変更が効いたかを、ここと比べて判定する。

### 段階 2 — 計測をステップ境界へ

**これが無いと、以降の段階が効いたかを判定できない。**

`by_agent` は実走行では `custom` 1 個に潰れ、エージェント別の按分が取れない。design が 78.5% であることは**フェーズ境界の差分**でしか分からず、内訳は見えない。

| 内容 | 変更 |
|---|---|
| 共通手順 `Fb` の契機 | フェーズ境界 → **ステップ境界** |
| 読み取りの鮮度 | **報告の直前に読み直すことを義務づける。** 現行は「読め」とだけ定め「いつ読むか」が無い |
| 受け口の再起動 | **`sink_started_at` の変化を検知する。** 変化していれば累計が 0 に戻っている |
| `cost-log.json` | **免除対象から外す。** 予算アラートの分母である |

**いずれも実害が観測されている。** 報告値の陳腐化は 2 回発生し（Phase 0 で 3 値の食い違い、design で 26 USD の乖離）、受け口の再起動は電源断で実際に起き、`cost-log.json` の免除は走行が無視したから助かった。

## 3. 横断して入れるもの（全形式に効く）

### 3.1 1 時間 TTL の扱い

キャッシュの TTL は 1 時間で、**失効を避ける手段は無い。** したがって規則は「失効させるな」ではなく「失効した後どうするか」を定める。

> **1 時間以上中断するなら、中断する前に `session-handoff` を作る。再開時は handoff が列挙した文書だけを読み直す。文脈が残っている前提で再開してはならない（MUST NOT）。**

**既存の `Fc` に契機を 1 つ足すだけである**（現在は `compaction_count` の増加が契機）。

**中心は handoff 側にある。** `session-handoff` に**「再開時に読む文書の一覧」を必須にする。** 一覧が無ければ再開側は安全に倒して全部読む。

### 3.2 要求の層に削る力を置く

**2 回目の最大の発見。** `NFR-006`（109 単位対で文字列一致 100%）は `user-order.md` に無く、**インタビューで生まれ**、厳密有理数と 2 コンポーネントを呼んだ。仕様書自身がこう記録している。

```text
ラウンド 3 の Q11 でユーザーがインタビューを終了した時点で、
削減候補として挙げられた要求は 1 件も無い
```

> **R2.18 は設計を最小構成と比較させる。要求を最小構成と比較させる機構が無い。**

**インタビューの終了条件に「削減候補の提示」を加える。** 各要求について「外すと何が起きるか」を 1 行。**外す判断はユーザーが行う。**

**これは質の施策であって量の施策ではない。** 要らない要求を落とせば、それを満たすための設計・テスト・レビューがまるごと消える。

### 3.3 仕様書の質の基準

> **書くべきは、有能な後段エージェントが 2 人いたとき、別々の答えに至りうるところだけである。同じ答えに至るなら書かない。それは記述ではなく複製である。**

**書くもの:** 外から来た値 / 他でもありえた判断と理由 / 却下した選択肢 / 規則が決めていない箇所の決着 / エージェント間の契約 / ユーザーの回答。

**書かないもの:** 規約の再説明 / コードから読めること / 規則を機械適用すれば出る結果 / 同じことの別記法 / 後段が必ず作るもの。

### 3.4 レビューは「変えるのが高いもの」に当てる

| 対象 | 変えるコスト | 誰が見るか |
|---|---|---|
| 設計 | **高い。** 後段がその上に積まれる | **人（別のエージェント）** |
| コード | 低い | **テストと lint** |

**根拠:** 対照実験の事後の自己点検は **PASS 39 / NA 8 / FAIL 0** で何も見つけなかった。同じ規約は**執筆中に**コードを変えている（外部 I/O のエラー捕捉に従い、パイプ切断の処理が入った）。

**準拠確認の記録は「該当なし」とその理由だけ残す。** 守った項目の羅列は、誰が書いても同じ文になる。

### 3.5 仕様形式はプロジェクト形式と独立

**仕様形式（ANMS / ANPS / StrictDoc）をプロジェクト形式で決めてはならない（MUST NOT）。**

| 軸 | 何で決まるか |
|---|---|
| プロジェクト形式 | **誰が読むか** |
| 仕様形式 | **分量と、関係を辿る回数** |

**簡易でも規模が大きければ ANPS。厳密でも小さければ ANMS。ANGS は未対応のまま。**

**現行の条文は「規模で決める」と書いてある。規模区分の廃止にあわせて書き換えが要る。**

## 4. StrictDoc の扱い

**採用は保留。判断材料は揃いつつあるが、決定的な確認が 1 件残っている。**

### 4.1 採る理由

**2 回目が最も明確に失敗したのがトレーサビリティである。**

| 観測 | 値 |
|---|---|
| 2 回目の `project-records/traceability/` | **0 件** |
| 義務づけている場所 | `CLAUDE.md`「必須プロセス設定」 |

**規則で必須としていたのに 1 件も作られなかった。** 手で維持するトレーサビリティは、実際には維持されない。

そして v3 §4.3 は、この対策案を「過大」として却下していた。

```text
C-4  トレーサビリティを機械化する（参照グラフで影響先を算出）
     却下理由: ANGS 相当の基盤が要る。過大
```

**StrictDoc の JSON 出力は、その基盤を自前で作らずに得る手段である。**

### 4.2 書く形式と辿る形式は分ける

**JSON からの取り込みは存在しない。** 取り込めるのは ReqIF と Excel のみで、**JSON は出力専用**である。

したがって「JSON で書いて `.sdoc` に変換する」には自前の変換器が要る。**標準があるものを自前で作らない**という本フレームワークの判断原則に反する。

> **書くのは `.sdoc`。辿るのは JSON。方向が違うだけで、両方を使う。**

**`.sdoc` を直接書く理由:**

| # | 理由 |
|:-:|---|
| 1 | **JSON 入力が無い。** 変換器の自作が要る |
| 2 | **出力 JSON は内部オブジェクトの写しであり、書くための形ではない。** トークンが減る保証も無い |
| 3 | **`.sdoc` は行単位で、git の差分が読める。** JSON は読めない |
| 4 | 散文は `>>> <<<` ブロックにそのまま書ける。JSON ならエスケープが要る |

**辿るときは `strictdoc export --formats json` を 1 回走らせる。** 要求・UID・関係の木が 1 つの構造になり、**2,908 行の散文を読み直さなくてよい。**

### 4.3 図の置き場

**図を要求本体から外す動機は正しい。** 図は大きく、人が読むもので、機械が辿ることはない。**外に出せば要求グラフと JSON が軽くなる。**

**ただし機構の確認が要る。**

| 分かっていること | 内容 |
|---|---|
| 画像 | `_assets` フォルダに置き、複数行フィールド内で reStructuredText 記法で埋め込む |
| Mermaid | `.sdoc` に**インラインで書ける**（`.. raw:: html` の `<pre class="mermaid">`。0.23.0+ では Markdown の ```mermaid フェンスも） |
| `DOCUMENT_FROM_FILE` | **`.sdoc` を取り込む機構であり、`.md` ではない** |
| `.md` の参照 | **`.sdoc` から Markdown ファイルを参照する機構は文書化されていない** |

**代替案:** 図は別の文書として同じプロジェクトツリーに置き、要求からは `RELATIONS: TYPE: File` で結ぶ。**これは要求とソースコードを結ぶために用意された機構であり、図にも使える見込みがある。未確認である。**

### 4.4 決定の前に確かめること

| # | 内容 | なぜ決定的か |
|:-:|---|---|
| **1** | **StrictDoc が Markdown を第一級の文書形式として扱えるか。** 0.27.0 の記述に「Format abstraction は SDoc, **Markdown**, ReqIF, RST, Excel, HTML, HTML2PDF, Doxygen, JSON を含む」とある | **もし Markdown のまま要求構造を持てるなら、`.sdoc` を書かずにトレーサビリティだけ得られる。** 器の違い・自前検査ツールが届かない・書くトークン増の懸念がすべて消える |
| 2 | 書くコストと辿るコストを分けた実測 | 懸念の大きさが確定する |
| 3 | `RELATIONS: TYPE: File` で図を結べるか | 図の置き場が決まる |
| 4 | `StrictDocStarter` の検証済み版は `0.23.1`、上流の現行は 0.27 系 | 差分の確認 |

> **1 を先に確かめる。** 結果次第で、以降の設計が大きく変わる。
