# トークン削減作戦ノート

**目的:** ざっくりした要求からヒアリングを行い、仕様書付きの高品質なソフトを作る。**その品質を落とさずにトークンを削る。**

**位置づけ:** `01-trial2-summary.md` の §8 に対する検討。**本ノートは検討であり、適用ではない。`framework-src/` はまだ変更しない。**

**根拠:** 数値は 2 回目トライアル（`gr-sw-maker-trial`）と対照実験（`unit-converter`）の実測である。**推定は推定と明記する。**

## 2. 施策 0 — 計測をステップ境界へ（採用済み・着手は保留）

**ユーザー判断: 採用。ただし本ノートに記録するのみで、いまは実施しない。**

**問題:** `by_agent` が実走行では `custom` 1 個に潰れ、エージェント別の按分が取れない。design が 78.5% であることは**フェーズ境界の差分**でしか分からず、**その内訳は見えない。**

**内容:** 共通手順 `Fb` の実行契機を「フェーズ境界」から「ステップ境界」に変える。`session-state.json` を読んで `cost-log.json` に 1 行足すだけである。

**根拠:** これが無いと、以降の施策 1〜3 が効いたかを判定できない。**効果の測れない削減は、品質を落としたかどうかも測れない。**

**コスト:** ほぼゼロ（ファイル追記のみ。エージェント起動を伴わない）。

**あわせて解消すべき既知の欠陥:**

| 欠陥 | 内容 |
|---|---|
| 報告値の陳腐化 | `Fb` は「読め」と定めるが「いつ読むか」を定めていない。**2 回発生**（Phase 0 で 3 値の食い違い、design で 26 USD の乖離） |
| 受け口の再起動 | `sink_started_at` の変化を検知する機構が無い。累計が 0 に戻っても鮮度マーカーは `OK` を返す |
| `cost-log.json` の免除 | Micro で免除されるが、予算アラートの分母である |

## 3. 施策 1 — 仕様書の質（量ではない）

**ユーザーの指摘により、方針を「量に歯止め」から「質の基準」に改める。**

### 3.1 判定基準

> **書くべきは、有能な後段エージェントが 2 人いたとき、**別々の答えに至りうる**ところだけである。**
>
> **同じ答えに至るなら、書かない。それは記述ではなく複製である。**

**「後のエージェントが分かることを書かない」を運用可能にした形である。** 「分かる／分からない」は主観だが、**「2 人が一致するか」は反例を 1 つ挙げれば決着する。**

### 3.2 書くべきもの — 後段が復元できない情報

| 種別 | 例（2 回目トライアルより） | なぜ復元できないか |
|---|---|---|
| **外から来た値** | 単位係数の一次定義（§3.4.5、70 行） | 外部の定義であり、導出できない |
| **他でもありえた判断と理由** | ADR 一覧（§3.6.2、97 行）、ADR-000 | コードは「何をしたか」を語るが「なぜ他を採らなかったか」を語らない |
| **却下した選択肢** | 増やさなかった 9 要素、§3.6.5 の「該当なし」11 件 | **最も失われやすい。** 記録がなければ次の担当が再検討する |
| **規則が決めていない箇所の決着** | FR-014 の丸めの同値ケース（ゼロから遠い側） | 規則に定めが無く、誰かが決めるしかない |
| **エージェント間の契約** | 公開面の宣言（§3.3.2） | 別のエージェントが実装する側と使う側を書くため、明示が要る |
| **ユーザーの回答** | インタビュー由来の要求、承認の事実 | 人間にしか出せない |

### 3.3 書くべきでないもの — 後段が復元できる情報

**以下は 2 回目の実物を判定した結果である。適用の可否は個別に判断する。**

| 対象 | 行数 | 復元できる根拠 | 判定 |
|---|---:|---|---|
| **Ch4 の Gherkin のうち、書式規則を機械適用すれば出るもの** | Ch4 836 行の一部 | §3.5.6 の出力書式規則と §3.4.4 の単位表から期待出力が計算できる | **要精査。** 規則が決めない場合だけ残す |
| **`3.4.1 クラス図`** | 93 | §3.2.2 責務表と §3.3.2 公開面表が同じ情報を持つ | **別記法の重複** |
| **`6.1 純粋性の分類`** | 52 | R7.6 が全関数に `@purity` タグを義務づけており、コードが持つ | **コードとの重複** |
| **`6.2` / `6.3` 設計原則の準拠確認** | 48 | review-agent が R1-R7 の Verdict を出す | **レビュー出力との重複** |

**注意:** 上表は「削れ」ではなく「**同じ情報が 2 箇所にある**」という指摘である。**どちらを正本にするかは別の判断であり、片方を消すときは参照の付け替えが要る**（文書管理規則 §6.1 の追随確認の対象）。

### 3.4 要求の層に削る力を置く

**2 回目の最大の発見:** `NFR-006`（109 単位対で文字列一致 100%）は `user-order.md` に無く、**Phase 1 のインタビューで生まれた。** それが厳密有理数を必要にし、2 コンポーネントを増やした。

仕様書 §2.3 の自己記録:

```text
全件がインタビューで合意された最小構成に対応する。
ラウンド 3 の Q11 でユーザーがインタビューを終了した時点で、
削減候補として挙げられた要求は 1 件も無い
```

**32 件すべて MUST、削減候補ゼロ。**

> **R2.18 は設計を最小構成と比較させる。要求を最小構成と比較させる機構が無い。**

**案:** インタビューの終了条件に「**削減候補の提示**」を加える。srs-writer が要求を確定する前に、「この要求を外すと何が起きるか」を各要求について 1 行で述べさせる。**外す判断はユーザーが行う。**

**これは質の施策であって量の施策ではない。** 要らない要求を落とせば、それを満たすための設計・テスト・レビューがまるごと消える。**乗数で効くのはここである。**

## 4. 施策 2 — レビューの再設計

**ユーザー指示:**

| # | 指示 |
|:-:|---|
| 1 | **design 完了前・実装開始前の 1 回**にする（抜け漏れ防止が目的） |
| 2 | **レビュワーが見るのは変化点だけ** |
| 3 | **レビュワーエージェントは起動を継続しておく** |

### 4.1 現状

design で**レビューが 3 回**回っている（`review-003` / `004` / `005`）。**1 回ごとに仕様書 2,908 行 + `review-standards.md` 511 行を読み直している。**

全走行では `review-001` 〜 `005` の 5 回。

### 4.2 3 の実現手段 — 継続起動は可能である

Claude Code のサブエージェントは通常 1 回ごとに新しい文脈で起動し、**そのたびに規約と仕様書を読み直す。**

**ただし継続する手段がある。** 一度起動したエージェントに追加の指示を送ると、**文脈を保ったまま続きを実行できる。** 2 回目以降は既読分がキャッシュに載っており、**読出（$0.50/M）で済み、書込（$10.00/M）が発生しない。**

**制約を 2 つ明記する。**

| 制約 | 内容 |
|---|---|
| **1 時間 TTL** | 間が空くとキャッシュが失効し、次のターンで全文が書き直される。**2026-07-31 の実測では 1 ターン $8.63、その 99.7% が `cache_creation`** |
| **文脈の単調増加** | 継続するほどレビュワーの文脈は伸びる。**読出は安いが 0 ではない**（$0.50/M） |

**したがって「継続起動」は無条件に安くはない。** 変化点レビューを短い間隔で連続して行う場合に効き、**フェーズをまたいで数時間空ける使い方では逆効果になりうる。仮説であり、施策 0 の計測で検証する。**

### 4.3 変化点レビューと追随確認の重複

**現状、同じことを 2 箇所でやっている。**

| 機構 | 契機 | 対象 |
|---|---|---|
| `C-3` 追随確認（文書管理規則 §6.1） | **生成時**（改訂した本人） | 図・ノート・影響を述べた行・ADR の Consequences・コード内の識別子 |
| review-agent | **事後** | 全文 |

**2 回目で `C-3` が実際に働いたことは確認済みである** — Ch3 の厳密有理数採用が Ch1.7 の L-7 の前提を壊したことを、レビュー前に自力で検出してユーザーに諮った。1 回目は同型の 7 件がすべて事後検出だった。

**したがって事後の全文再読は、生成時の追随確認と二重になっている。** 変化点に絞る根拠がここにある。

### 4.4 残る懸念

**変化点だけを見ると、変化していない箇所どうしの矛盾は見つからない。** 現状はそれを全文再読で拾っている。

**緩和案:** 1 回だけ残すレビュー（実装開始前）を**全文 1 回**とし、それ以外を変化点に絞る。**ユーザー指示の「design 完了前・実装開始前の 1 回」はこの位置にあたる。**

## 5. 施策 3 — エージェントが読む規約を絞る

**8,193 行が毎回の固定費である。** 上位 2 文書で 59.1%。

### 5.1 手段の比較

| 案 | 内容 | 長所 | 短所 |
|:-:|---|---|---|
| **A** | 大きい 2 文書を章単位のファイルに分割し、エージェント定義に「読む章」を書く | **確実。読む範囲が定義で固定される** | ファイル数が増える。`check-links` の参照更新が要る |
| **B** | **スキルに書く**（必要時に読み込まれる） | **段階的な開示ができる。** 本体を小さく保てる | **読み込みがモデルの判断に依存する。** 必要な条を読まない可能性がある |
| **C** | 現状維持 | 変更が要らない | 930 起動すべてに 8,193 行が乗る |

### 5.2 検討

**B（スキル）は魅力的だが、規約には向かない面がある。** スキルは「必要と判断したら読む」機構であり、**MUST の条文を読まなかった場合に違反が黙って通る。** 施策 0 の計測では違反は検出できない（コストしか見ない）。

**A は確実だが、分割の粒度を誤ると「必要な条が別ファイルにあって読まれない」という同じ失敗になる。**

**折衷案:** **MUST の条文と、判定に使う表は本体に残す。** 解説・背景・例示をスキルまたは別ファイルへ出す。**「なぜ」を分離する。**

**ただしこれは B-7（既定値と MUST に理由を併記する）と正面から衝突する。** B-7 は「理由が書かれていない規則が繰り返し読み替えを必要とした」ことを根拠に採用された。**理由を遠ざけると、その効果が失われうる。**

> **未解決。** 「理由は判断のときに要るが、毎回読む必要はない」が成り立つかは検証されていない。**施策 3 は施策 1・2 より後に置く。**

## 6. 着手順序

| 順 | 施策 | 根拠 | risk |
|:-:|---|---|---|
| **1** | **施策 0（計測）** | **これが無いと以降の効果を判定できない** | 無し |
| **2** | **施策 1（仕様書の質の基準 + 要求層の削る力）** | **乗数で効く唯一の層。** 要求が減れば設計・テスト・レビューがまるごと減る | 中。要求を削りすぎると品質が落ちる。**判断はユーザーが行う** |
| **3** | **施策 2（レビューの再設計）** | design が 78.5% を占め、その中でレビューが 3 回回っている | 中。**変化点に絞ると、変化していない箇所どうしの矛盾を落とす** |
| **4** | 施策 3（規約の分割） | 固定費に効くが、B-7 との衝突が未解決 | **高。** MUST を読み落とすと違反が黙って通る |

**施策 2 と 3 の順序について:** ユーザー指示ではレビューの変更が先に述べられているが、**施策 0 を先に入れないと、レビュー削減がコストに効いたのか品質を落としたのかを分離できない。**
