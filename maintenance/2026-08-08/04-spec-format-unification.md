# 仕様形式を StrictDoc の `.md` 方式へ一本化できるか — 検討と計画

**本書は検討と計画である。着手していない。StrictDocStarter は参照のみで、編集していない。**

**問い:** ANMS / ANPS / ANGS の 3 形式を、StrictDoc の Markdown 方式に統一できるか。

---

## 1. 結論

> **統一できる。そして統一すると、ANMS / ANPS / ANGS という 3 段階の区分そのものが要らなくなる。**

**理由は 1 行で言える。**

> **3 段階は「表現の違い」として定義されているが、StrictDoc の `.md` に統一すると、残る違いは「ファイルの枚数」だけになる。枚数は形式ではない。**

現行の定義を並べれば分かる。

| 形式 | 現行の定義 | StrictDoc `.md` にすると |
|---|---|---|
| ANMS | **単一 Markdown ファイル** | `.md` 1 枚 + 文法 1 枚 |
| ANPS | **複数 Markdown + Common Block** | `.md` 複数枚 + 文法 1 枚 |
| ANGS | **GraphDB + Git（MD はビュー）** | **GraphDB を捨てれば、上の 2 つと同じもの** |

**ANMS と ANPS の違いは枚数だけになる。** ANGS だけは「GraphDB」という別の実装を指しているが、**これは未対応のまま一度も実現していない。**

## 2. なぜ統一できるのか — 決め手は 2 つ

### 2.1 記法は依存を持たない。検証だけが依存を持つ

**これが最大の発見である。** StrictDoc の `.md` は、素の Markdown に見出しとフィールドを置いただけである。

```markdown
## 要求の名前

**UID**: SW-001 \
**STATUS**: Approved \
**REVIEW_STATUS**: NoFinding

**Statement**: 本システムは、 〜すること。

**Relations**:
- **Type**: `Parent` \
  **ID**: `SYS-001`
```

**この形を書くのに strictdoc は要らない。** テキストエディタで書ける。GitHub でそのまま読める。**Python も jq も要らない。**

**要るのは検証するときだけである。**

| したいこと | 要るもの |
|---|---|
| **書く** | **何も要らない** |
| 文法違反を捕まえる | `strictdoc export` |
| 関係を辿る・抜けを探す | `strictdoc export --formats=json` + `jq` |
| HTML で読む・表で並べ替える | `strictdoc export --formats=html` |

> **これは改良計画の 3 形式（簡易 / 通常 / 厳密）と正確に噛み合う。** 簡易は書くだけで検証を回さない。通常と厳密は回す。**記法は 3 形式で同じでよい。**

### 2.2 構造の誤りが export で止まる — 自前の検査が要らなくなる

**StrictDoc は 9 種類の構造違反で export を止める**（実測済みの一覧が `00-ai-guide.md` にある）。

そして重要なのはこれである。

> **リンク切れと UID の重複にクエリは要らない。どちらも StrictDoc が関係を解決する段階で export を止め、JSON を 1 バイトも書かないためである（実測）。JSON が手元にある時点で、その 2 つは無い。**

**gr-sw-maker は今、同じことを自前でやっている。**

| 現行の自前検査 | StrictDoc に統一すると |
|---|---|
| `check-links`（118 リンク + 269 節参照） | **要らなくなる**（export が止まる） |
| `check-tagnames` | **要らなくなる**（`SingleChoice(...)` が値域を強制する） |
| `check-terms` | **残る。** StrictDoc に語彙検査は無い |
| `check-parity` / `check-roster` / `check-setup` | **残る。** フレームワーク自身の検査であり仕様書の検査ではない |

## 3. 統一後の姿

### 3.1 軸が 1 本減る

**現行は 2 軸ある。**

```text
仕様形式:     ANMS  /  ANPS  /  ANGS        ← 分量と関係の辿り方で決める
プロジェクト形式: 簡易  /  通常  /  厳密      ← 誰が読むかで決める
```

**統一後は 1 軸になる。**

```text
記法:         StrictDoc の .md （1 つだけ）
プロジェクト形式: 簡易  /  通常  /  厳密      ← 誰が読むかで決める
             ↑ ここが「文法（.sgra）の豊かさ」と「検証を回すか」を決める
```

| プロジェクト形式 | 文法（`.sgra`） | 検証 | ファイル枚数 |
|---|---|---|---|
| **簡易** | 最小（`SECTION` / `REQUIREMENT` / `USE_CASE` / `TEST_CASE`） | **回さない。書くだけ** | 分量なりに 1〜数枚 |
| **通常** | 標準（上記 + `STATUS` / `REVIEW_STATUS` / `Rationale`） | **json + html + 抜けの検出** | 分量なり |
| **厳密** | 拡張（+ 独自ノード型・`Role` つき関係） | 上記 + 監査クエリ一式 | 分量なり |

> **「1 コンテキストウィンドウに収まるか」は、もはや形式を決めない。** ファイルを何枚に割るかを決めるだけであり、**それは StrictDoc がフォルダ単位で扱うので自動的に成立する。**

**ノードになるのは 7 種類、解説は残り全部である。**

#### 段 3 で決めたこと

| # | 決定 | 理由 |
|:-:|---|---|
| 1 | **`ND` / `CN` をノード型にする**（`NODE` / `CONNECTION`） | **ID を振ると決めた以上、機械が検証できないと ID の意味が半減する。** 型にすれば、NFR の `効く対象` が実在しない `CN` を指した瞬間に export が止まる |
| 2 | **Ch3.3 を独立ノードにしない** | 主成功シナリオと拡張は 1 つのユースケースの中身である。**別ノードにすると、拡張 1 件ごとに UID の維持が要る** |
| 3 | **Ch4.3 の削減候補の表を作らない** | **`D17`（親を持たない要求）が同じものを出す。** 手で書く表は、書かれなくなる（2 回目トライアルのトレーサビリティ 0 件）。**ただし消えるのは段 4 以降である** — StrictDoc へ移るまでは、手書きの表が唯一の機構なので `00-spec-template-draft.md` §4.3 は残す |
| 4 | **ADR をノードにしない** | 設計判断をトレース対象にすると層が 1 つ増える。**必要になってから型を足せばよい** |
| 5 | **FR と NFR を同じ `REQUIREMENT` 型にし、`REQ_KIND` で区別する** | 親の型が違う（`USE_CASE` / `GOAL`）だけで、要求としての性質は同じ。**ただし「どちらか」は文からは読めないので、欄が要る** |

> **決定 5 は「EARS の型を欄に持たない」と矛盾しない。** EARS の型は**要求文そのものに現れる**ので欄にすると二重管理になる。**機能か非機能かは文から読めない**ので、欄が唯一の情報源になる。

#### NFR が持つ 2 種類の関係

```text
NFR-001 ──Parent──▶ GOAL-001            鎖（削減候補の判定に使う）
NFR-001 ──Parent(Role: Affects)──▶ CN-001   効く対象（セキュリティ設計の起点）
```

**`ROLE` で区別する。** 鎖を辿るクエリは `ROLE` の無い関係だけを見る（`01-ai-queries.md` の `C15` が `ROLE` で絞る手を持っている）。

**これを怠ると、`D17`（親を持たない要求）が `Affects` の関係も親として数えてしまい、削減候補の検出が壊れる。**

### 3.3 `.sgra` はガバナンスである### 3.3 `.sgra` はガバナンスである（ユーザー決定）

**`.sgra` は必須とする。** 分量が小さくても省略しない。

**これは代償ではなく、統一の目的そのものである。** 現在、仕様書の「何を書かねばならないか」は `spec-template`（v0.35 で 806 行）の散文が担っている。**散文の規約は、守られたかどうかを機械が判定できない。**

```text
現行:  spec-template の散文        →  人（review-agent）が読んで判定する
統一後: .sgra の宣言               →  export が止まる。判定の余地が無い
```

**`.sgra` へ移るもの:**

| 現行 spec-template が散文で書いていること | `.sgra` での姿 |
|---|---|
| どの章にどのノードを置くか | `TAG` の宣言 |
| どのフィールドが必須か | `REQUIRED: True` |
| 値域（`sea` のみ、`PASS/FAIL/SKIP` など） | `SingleChoice(...)` |
| 何と何を紐づけてよいか | `RELATIONS` の `TYPE` / `ROLE` |

> **`spec-template` の性質が変わる。** 「規約」から「なぜその形なのかを説明する手引き」へ移る。**強制するのは `.sgra` である。**

**そしてプロジェクト形式の選択が、`.sgra` の選択になる。**

```text
簡易 → 最小の .sgra を配る
通常 → 標準の .sgra を配る
厳密 → 拡張の .sgra を配る
```

改良計画の `apply-process-mode.js`（仮称）が「形式ごとの文書一式を配置する」と定めているが、**配るものの中身がこれで具体化する。**

### 3.4 削減候補の検出が jq 1 行になる

**v0.35 §4.3 は削減候補を手で表に書かせている。** StrictDoc なら既存クエリがそのまま使える。

| v0.35 の規則 | 対応するクエリ |
|---|---|
| どのユースケースにも紐づかない FR | **`D17` 親を持たない要求** |
| どの目標にも効かないユースケース | **`D17`**（`USE_CASE` に適用） |
| どのノード・接続にも効かない NFR | **`D17`** |
| （v0.35 に無い）誰からも参照されない要求 | **`D18`** |
| （v0.35 に無い）テストに覆われない要求 | **`D16`** |

> **手で維持する表が 3 本消え、クエリ 3 本に置き換わる。** 2 回目トライアルの `project-records/traceability/` が **0 件**だった事実に対する、最も直接的な答えである。

## 4. 代償 — 正直に並べる

| # | 代償 | 重さ |
|:-:|---|---|
| 1 | **`.md` 入力は StrictDoc の experimental 機能である** | **最大のリスク。** 公式文書に experimental の表記が残る（`04-strictdoc-evaluation.md` で確認済み） |
| 2 | **`.sgra` を必ず 1 枚書く**（ユーザー決定。ガバナンスとして必須とする） | 「単一ファイル」が崩れ、最小 2 ファイルになる。**代償ではなく設計である。§3.3 を見よ** |
| 3 | **`.md` の雛形と `.sgra` は対でなければならない** | フィールドを 1 つ宣言し忘れると export が止まる。**止まるので気づける** |
| 4 | **Common Block と StrictDoc がファイルの先頭を奪い合う** | **最大の実務上の障害。** §4.1 を見よ |
| 5 | **検証には Python + strictdoc + jq が要る** | 簡易は回さないので影響しない。**通常・厳密は前提が増える** |
| 6 | **JSON から `.md` へ機械的に戻せない**（JSON にファイルパスが無い） | 書き換えは `.md` を開いて行う。**手順は `00-ai-guide.md` が 7 段で持っている** |
| 7 | **並列 export が本当のエラーを握り潰す**（strictdoc 0.27.1 の不具合） | `--no-parallelization` を必ず付ける。**規約に書けば済む** |

### 4.1 Common Block と StrictDoc の衝突（最大の実務上の障害）

**Common Block とは YAML frontmatter である。** `document-rules` 第 5 章が定義する。

```yaml
---
okf_version: "0.2"
type: spec-foundation
description: {summary}
document_status: approved
document_version: "1.2"
owner: srs-writer
consumed_by: [architect, review-agent]
generated: {by: ..., at: ...}
updated:   {by: ..., at: ...}
---
```

**Open Knowledge Format (OKF) v0.2 に従う容器であり、管理対象文書すべてに付く**（仕様書に限らない）。中身は文書の管理情報である — 誰のものか / 誰が次に使うか / 承認済みか / いつ誰が触ったか。`{namespace}` の下に file_type 固有の Form Block がぶら下がる。

**役割は StrictDoc のフィールドとほとんど重ならない。**

| Common Block | StrictDoc `.md` |
|---|---|
| `owner` / `consumed_by` / `commissioned_by` | **無い**（エージェント間の受け渡しは StrictDoc の関心事ではない） |
| `generated` / `updated` | **無い** |
| `type`（file_type） | **無い**（`Grammar` が近いが別物） |
| `document_version` | `Version` **← ここだけ重なる** |
| `document_status` | 要求ごとの `STATUS` はあるが、**文書単位は無い** |

**問題は重複ではない。置き場所である。**

```text
Common Block の規則     : ファイル先頭に `---` で囲んで置く（MUST）
StrictDoc の停止規則     : ファイルの先頭を H1 で始める
                          → error: the document must start with an H1 heading
```

> **同じファイルの先頭を、2 つの規約が奪い合う。**

### 4.2 測定した（2026-08-08。strictdoc 0.27.1 / Python 3.13.3）

**`.md` 1 枚 + `.sgra` 1 枚の最小構成で 7 通り測った。**

| 変種 | Common Block の位置 | 終了 | 実際に起きたこと |
|---|---|:-:|---|
| 対照 | 無し | 0 | 正常。文書 UID・要求とも通る |
| **先頭** | **規約どおりファイル冒頭** | **1** | **`the first content of the document must be an H1 heading`**（`_validate_no_content_before_h1()`） |
| 後ろ置き | H1 の直後 | **0** | **通るが文書ヘッダが消える。`UID` が `null`。`**Grammar**` も地の文へ飲まれる** |
| 後ろ置き＋宣言済フィールド | H1 の直後 | 1 | `Invalid requirement field: REVIEW_STATUS` — **文法が読まれていない証拠** |
| 独自の文書フィールド | 無し（`**Owner**:` を追加） | **0** | **`Owner` が JSON から跡形もなく消える**（grep 0 件） |

**結論は 3 つある。**

| # | 結論 |
|:-:|---|
| 1 | **先頭に置くのは不可能である。** 明示的に弾かれる。回避策は無い |
| 2 | **H1 の後ろへ逃がすと、文書ヘッダ（`Grammar` / `UID` / `Version`）を丸ごと失う。** 文法が適用されなくなる |
| 3 | **文書ヘッダに独自フィールドは置けない。** エラーも警告も出さずに消える |

> **2 と 3 により、§5.2 の案 B と案 C は成立しない。**

**あわせて 1 つ、静かに壊れる経路を見つけた。終了コード 0 で通る。** 詳細と再現手順は `05-strictdocstarter-feedback.md` にある（`StrictDocStarter` へ返す指摘として記録した）。

| 経路 | 起きること |
|---|---|
| 文書ヘッダに未知のフィールドを書く | **エラーも警告も無く消える。** 要求のフィールドは未知ならエラーになるのに、文書のフィールドは黙って捨てられる |

> **後ろ置きの失敗の仕方は一定しない。** 「`Invalid requirement field: Grammar` で落ちる」ときと「通るが文書ヘッダを失う」ときの両方を観測した。**どちらでも使えないという結論は変わらない。**

## 5. 判断が要る 3 件

### 5.1 Chapter 2 System Configuration をノードにするか（段 3 で決着）

**決定: `NODE` と `CONNECTION` の両方をノード型にする**（§3.2 の決定 1）。

**当初は「`CONNECTION` だけ型にする」を推していた。** 変えた理由は 2 つある。

| # | 理由 |
|:-:|---|
| 1 | **`ND` / `CN` を ID 付きの接頭辞として残すとユーザーが決めた。** ID を振るのに機械が検証しないなら、ID は飾りになる |
| 2 | **`CONNECTION` だけを型にすると、その `From` / `To` が指す先が型を持たない。** 参照の片側だけを検証する形になり、リンク切れの検出が半分しか効かない |

**md-basic-ja の「設計をトレースの対象にすると層が 1 つ増える」という警告は、ここには当たらない。** あちらが指しているのは**設計（内部構造）**であり、Chapter 2 は**与件（物理配置）**である。**選んだものではないので、設計判断の層は増えない。**

### 5.2 Common Block が落ちた場合にどうするか

**§4.2 の実測により、選択肢は 2 つに減った。**

| 案 | 内容 | 状態 |
|:-:|---|---|
| **A** | **仕様書だけ Common Block を外し、管理情報を横に置く**（`my-app-spec.md` に対する `my-app-spec.meta.yaml`） | **実質唯一の道** |
| ~~B~~ | ~~最小限を StrictDoc の DOCUMENT フィールドへ写す~~ | **消えた。** 未知の文書フィールドは無言で消える（§4.2） |
| ~~C~~ | ~~Common Block を「H1 の直後」へ移す~~ | **消えた。** 文書ヘッダと文法を失う（§4.2） |
| D | 仕様書を StrictDoc 化しない。統一を諦める | 本書の利得すべてを失う |

**A の姿:**

```text
docs/spec/my-app-spec.md         ← StrictDoc の .md（先頭は H1）
docs/spec/my-app-spec.meta.yaml  ← Common Block（OKF v0.2 のまま）
```

**代償は 2 ファイルの同期である。** ただし機械で検査できる。

| 足す検査 | 内容 |
|---|---|
| `check-spec-meta`（仮称） | `.md` と同名の `.meta.yaml` が在るか / `type` が登録済みか / `updated` が `.md` の更新より古くないか |

**A を採るなら、`document-rules` の「Common Block は全管理対象ファイルの先頭に置く（MUST）」に例外が 1 つ増える。** 例外を作る以上、**なぜ仕様書だけ違うのかを規則側に書く**（`framework-development.md` §5.5 の様式に従う）。

**A を推す。** 仕様書は要求グラフを持つので StrictDoc の利得が大きい。**`decision` / `review` / `risk` などのプロセス記録は要求グラフを持たないので、寄せる理由が薄い。**

> **ただし `04-strictdoc-evaluation.md` は「Common Block との併存は見積もられていないコスト」と書いている。** ここは改良計画の段階 4（`document-rules` の file_type 分割）と同じ問題を扱っており、**別々に決めると矛盾する。**

### 5.3 ANGS をどうするか

### 段 4 で判明した設計の誤り — 鎖の判定条件

**段 3 は「`ROLE` の無い関係が鎖である」と決めていた。これは誤りである。**

`TEST_CASE` の親は `Role: Verifies` を持つ。**「`ROLE` 無しだけを辿る」規則では、シナリオが鎖から外れて全件が孤立扱いになった**（実測）。

```text
NG  TEST_CASE  SC-001    ← 誤検出
NG  TEST_CASE  SC-002    ← 誤検出
```

**直した判定:**

> **鎖に載る関係には必ず `ROLE` を付ける — `Satisfies`（要求・ユースケースが目標を満たす）と `Verifies`（シナリオが要求を検証する）。**
> **鎖の外の関係は `Affects`（NFR が効くノード・接続）と `From` / `To`（接続の両端）である。**

**「`ROLE` の有無」ではなく「どの `ROLE` か」で判定する。** 直した後の実測:

```text
OK  USE_CASE UC-001 / REQUIREMENT FR-001 FR-003 FR-005 NFR-005 / TEST_CASE SC-001 SC-002
NG  REQUIREMENT NFR-098（Affects だけを持つ）
NG  REQUIREMENT NFR-099（関係を 1 つも持たない）
```

**`NFR-098` は、段 3 で警告した罠をそのまま仕込んだものである。** `Affects` の関係だけを持ち、鎖の親を持たない。**`ROLE` を見ない検出はこれを取りこぼす**ことも実測で確かめた。

### 段 4 で判明した実務上の注意

| # | 内容 |
|:-:|---|
| 1 | **`Grammar:` のパスは文書自身の位置からの相対である。** `_assets/` に置いた文書が `anms.sgra` を参照すると、見つからず export が止まる。**`md-basic-ja` は図の文書に `Grammar` を宣言せず、既定文法に任せている。** 同じにした |
| 2 | **`.sgra` と `.md` は対で直す。** 文法に `ROLE` を足して文書を直し忘れると `Requirement relation type/role is not registered: Parent` で止まる（実測） |
